## PRECISION CHECKLIST (the generic one - five measured defect classes)
Measured on the first code engagement: of 882 round-1 scorings 726 were confirmed, 104 imprecise, 11 false. The conclusions were almost always right; what failed was the precision of the sentence carrying them. Writers apply every class before reporting; the client critic scores against them.
1. **Figure without its predicate** (45 % of all defects). The claim names what was counted, over which paths, under which convention; the figure comes from `dbcx count` or the method's counter, not an ad-hoc pipeline; an enumeration in the same claim sums to its headline; a percentage carries its denominator; a figure that disagrees with the inventory or handover names both figures - a declared disagreement is a finding, a hidden one a defect.
2. **Code state stated as runtime state.** A behaviour claim ("the shop does X") names its ENTRY POINT (route/controller, process action, job or trigger, listener or event, API endpoint) and the repository CONFIGURATION under which it is reachable (property value along the effective chain, flag, activation of the module, wiring/alias, the template actually rendered). Without that, write what the code contains and that no caller or wiring is in the snapshot. Examples: a config flag makes a branch unreachable; a config macro does not prove the value reaches the running system; a scanner hit is tested against its activation property; a route named after a capability can be a diagnostic page; check what a method passes on, not only what it reads; an enum value needs a reachable transition; the rendered UI path decides whether a feature is on; for an overridden or aliased bean or class, state which copy actually executes. A wrong runtime claim is `unsupported`, not imprecise.
3. **Locator that does not carry the fact.** Cite the line that contains the fact (the template name, the attribute, the hit), not the file of the topic; an aggregate row names its package path; a fact from the finalized inventory is cited by its claim id or locator, not re-derived.
4. **Right verdict, wrong premise.** When a reference row or a repository fact is the justification, quote what it says (optional vs mandatory, default vs configured, the sentence of a multi-sentence row); an overriding class is diffed against the shipped TARGET-version class, not the version the workaround was written for; one proposition per claim, so a wrong premise cannot sink a verified finding.
5. **Absolutes and enumerations.** "No", "all", "every", "never" are proven structurally - name the family searched and a pattern that covers it (type names with digits and underscores included) - or restricted to what was checked; an enumeration is complete.
Not asked: padding, hedges that hollow out a finding, a softened verdict. Precision means the sentence survives someone who greps it.
