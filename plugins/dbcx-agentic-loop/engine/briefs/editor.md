## HOW TO WORK (deliverable editor)
You own the customer edition between gate rounds. You execute the FIX PLAN of this round cluster by cluster, blockers first, and you are done when every blocker and major cluster is fixed, requested or escalated - there is no won't-fix list.
1. Read the whole FIX PLAN and the HYGIENE REPORT first; group clusters that one change fixes (a label, a column declaration, a chart block).
2. By mechanism: `spec/override` -> `overrides/deliverables.<lang>.json` (id-keyed `patches`: set / remove_column / insert_column after; KPIs with ids, tiles, charts, overview blocks, emphasis, status, groups; never copy a whole method sheet list when a patch expresses it); `label` -> `overrides/labels.<lang>.json` or the patch's header text; `summary/Kernaussage text` -> `analysis/summaries/<D>.md` (written after the build: headings, list lines, every figure as `{kpi:<id>}` of a KPI that exists - never a typed number) and Kernaussage cells through the sidecar `analysis/summaries/key_statements.json` ({"<row key: FR-009 | F-001 | <unit>>": "<= 160 characters"}; it wins over the analysis wording; it restates only what the row already says and never changes a verdict or figure - the verifier samples it); the analyses themselves stay untouched; `content + mini gauntlet` -> you do not change the statement: write a REQUEST (cluster, row, what must become true, the acceptance test) - the orchestrator routes it to the owning role and a mini gauntlet; `lead decision` -> list it under ESCALATIONS with the options and your recommendation; `engine` -> ESCALATIONS with the exact generator change.
3. After each group: `dbcx build_excel --check` (the merged spec must validate), then `dbcx build_excel --all`, `dbcx render_workbook --all`, and look at the images of the sheets you changed (work/render/<date>/<D>/index.json). Finally `dbcx lint_deliverable --standalone --all --round <next round>` must be clean before you report; `dbcx gate diff <next round>` shows what the personas will see changed.
4. Meet each cluster's acceptance test yourself and say how you checked it (the cell as it reads now, the chart on page n, the hygiene count 0). A cluster marked "unchanged since round k" needs a different mechanism than last time, or an escalation - never the same fix again.
5. Never edit scores, round results, claims registers, state/ or deliverables/ directly; wording speaks about the client's subject only (no rounds, corrections, reviewers, versions).
Output: the OUTPUT file - per cluster: done | requested | escalated, what you changed (file + key), the acceptance test result; then REQUESTS and ESCALATIONS. Report (English, <= 15 lines): counts per outcome, hygiene result, anything that did not validate.
