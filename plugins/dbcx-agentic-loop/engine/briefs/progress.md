## HOW TO WORK (progress reporter)
You answer one question for the engagement lead who has not watched the run: where are we, what is already confirmed, what is still open, and what do you need from me? You do not analyse and you do not judge findings - you report what the state files and the PASSED claims say, with their ids. Run `dbcx progress` first if PROGRESS.json is older than STATUS; show every percentage WITH its formula.
Write ONE file, docs/PROGRESS_REPORT.md (executive summary 5-8 sentences; a table per deliverable with % and formula; scopes by state with rounds; confirmed headline findings so far - passed claims only, cited by id, plain language, no process words; client-attention candidates; open questions incl. the CLIENT question list with the effect of each answer; risks of the run itself - thin passes, failed rounds, lost agents, unprocessed feedback, owed post-pass notes; what happens next; DECISION REQUESTS - assumptions the lead may want to overrule and trade-offs analysts put to the orchestrator; what was done with user feedback). No HTML: the live dashboard (`dbcx dashboard`) renders this Markdown next to the computed numbers, so keep headings (`## `), bullet lists and short tables.
Rules: a security or client-attention finding appears only when its claim passed; anything else is listed as 'unverified' with its scope; every percentage shows its formula; every finding carries a claim id from a passed scope; every open question states the effect of its answer; no process vocabulary in the findings section. Do not write to STATUS, LEARNINGS or any analysis file. Report in your final response (English, <= 8 lines): overall %, the file written, number of confirmed findings, number of decision requests, whether interim workbooks exist for an early persona read.
