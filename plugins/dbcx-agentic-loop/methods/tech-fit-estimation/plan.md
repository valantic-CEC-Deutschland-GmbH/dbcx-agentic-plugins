# Orchestration plan – {engagement.client}: fit estimation of the requirement list per solution option

Trigger: the user says **"Execute the plan"** after (a) `dbcx check_fill` reports 0 placeholders, (b) `dbcx smoke tech-fit-estimation` ends with SMOKE TEST OK, (c) the client's requirement list is in `input/requirements/` (or a released `requirements-set` is imported). Run everything below without asking questions; decisions go to `state/STATUS.json` → `assumptions[]` (`dbcx status assume ...`). Resume point after any interruption or context compaction: `dbcx status verify`, then `dbcx status next`. "How far are we?" at any time → the `progress` sub-command (no fixed cadence). Feedback given in chat during the run → `dbcx status feedback add "..."` immediately.

Plugin: `{plugin}` (tools `dbcx <tool>` or `python3 {tools}/<tool>.py`; roles are the plugin agents `dbcx-agentic-loop:<role>`). Every agent is spawned from a brief FILE: `dbcx render brief ... --out [--addendum <file>]` writes `analysis/briefs/<agent>[-rN].md` and prints path, MODEL and agent name; the prompt references the path (the spawn hook checks path and model and registers the agent in `in_flight`). Rounds ≥ 2 need `--addendum <file>` (or `--no-addendum`). Critics stay alive per scope: later rounds are SendMessage calls with the new delta, not new spawns.

**One run, N options, one workbook.** An option = technology × starting point, declared in `run.json` → `options` (`id`, `label`, `pack`, `start` greenfield | brownfield, `version`, `plan`, `frontend`); without `options` the one option is **{target.platform} {target.version}** (plan/edition {target.plan}, frontend {target.frontend}). Two starting points on one platform (migration vs rebuild) and two technologies side by side are the same run shape. Unit of analysis: a chunk of the requirement list — `state/scopes.json`, names `epic-NN`, epic texts in `meta.EPICS`; every chunk is estimated for every option. Sizes are {estimation.size_term.en} tokens; the workbook's Parameter sheet maps them to {estimation.unit}, adds the PM / SA / BA / QA surcharges per option and prices at the day rate ({estimation.day_rate} {estimation.currency} by default). Deliverable in `{languages.deliverable}`; chat and agent reports English.

| | Deliverable | Built by (orchestrator only) | From |
|---|---|---|---|
| D1 | `deliverables/{deliverables.D1.file}` | `dbcx build_excel D1` | `analysis/scopes/*.md` + `analysis/consolidated/SUMMARY.md` + `analysis/summaries/D1.md` + `input/handover/*.json` |

**Row classes and scenarios.** Rows of three classes: the client's requirements (every option), technical migration rows TM-nn (necessities of the move no client row describes, every option) and refactoring rows RF-nn (clean-core / quality changes, brownfield options only) from the lead-approved classification of the code-analysis handover (`dbcx classify`). Per row and option also the effort on the integration platform (`run.json → estimation.integration_platform`, own {estimation.size_term.en} column) and, for a refactoring row, the migration effort it saves on the client rows it names. The workbook totals per SCENARIO (`run.json → scenarios`: an option, the classes it counts, optionally minus the savings; without the key one scenario per option): platform development, saving, PM / SA / BA / QA, fixed phases per scenario (starting values `estimation.fixed_phases_seed`), integration platform development with the same surcharges, total and cost - sheet Szenarien, and Summen, Vergleich, Zuschlaege_und_Phasen and the Management Summary sum the same lines. The estimate is written for a product owner: no file, class, package, extension name or line number in any text, and no code location in either edition of the workbook (the basis of a code-analysis fact reads "Code-Analyse · <id>").

With more than one technology pack among the options, the standard side is one critic per pack (`standard-<pack>`, agent `critic-standard-<pack>-<scope>`): each scores the claims of its pack's options and the option-neutral ones; the client critic scores every claim.

## Phase 0 – Preflight (orchestrator) - the setup order matters
1. `dbcx check_fill` → 0 placeholders (`target.version`, `target.plan`, `target.frontend`, `deliverables.D1.file`, the `platform` knowledge slot, every option's pack). `dbcx smoke tech-fit-estimation` → SMOKE TEST OK. `dbcx md_to_json --generate`.
2. Handover imports BEFORE the intake: the requirement list (`dbcx requirements_to_json` with `requirements_mapping.json` filled - compare row count and first / last id with the client's file; or `dbcx handover import requirements-set`); for a brownfield option the code analysis of today's shop: `dbcx handover import requirements-coverage`, `... target-readiness`, `... customization-depth`, `... code-inventory` (cited as `HO-<type>#<id>`, never restated as our own); the client's answers to an earlier run's assumptions: `dbcx handover import client-assumptions`, then `dbcx questions import-handover input/handover/client-assumptions.json` (A-nn and answers kept - an answer by the client is a fact; this run's own assumptions number on after the highest imported A-nn). A brownfield option also sets `repo.path` to the frozen client repository (evidence base `client-repo`, narrow lookups only).
2b. Several systems (run.json `systems`): the landscape FIRST, so the requirement import resolves the system names - freeze the client's system list (`dbcx handover import <file.csv|xlsx> --as landscape`) and convert it (`dbcx landscape_import input/handover/<file> [--sheet S] [--map id=<col>,name=<col>,kind=<col>,description=<col>,owner=<col>,aliases=<col>]`), or take an ea-landscape run's artefacts (`dbcx handover import system-inventory`, `... data-flows`, then `dbcx landscape_import input/handover/system-inventory.json input/handover/data-flows.json`) -> `state/landscape.json` with ALL the customer's systems, also those this run does not estimate. The mapping's group keys: `kind: interfaces` (columns `from` / `to` / `via`), `estimate: false` (reference rows), `systems_field`, `rollup_to_field`, `passthrough: true` (the client's sheet carried unchanged; needs `columns.id`). Then `dbcx requirements_to_json` and `dbcx build_excel --check`: it refuses mapping-key errors, unknown roll-up targets and a passthrough sheet without an id column, and lists the system names and interface ends that resolve to no system of the run (an end at a landscape system outside the run stays recorded for the architect). A later landscape import refreshes the pre-fill of `state/requirements.json`.
3. Vendor standard code (when an option uses the composable storefront): `dbcx vendor_code resolve --line <release line>` then `dbcx vendor_code install --version <v> --root reference/vendor-code/composable-storefront` (the registry credentials stay in the lead's own npm configuration - never in a file of the engagement, a log or a brief); `dbcx vendor_code verify` afterwards. The tree is read-only evidence (base `vendor-code`), cited through reference rows only.
4. Optional client material: `dbcx corpus index` over `input/` so readings can cite `SRC-nnn#anchor`.
5. `dbcx intake` — defects of the list become client assumptions or questions on the workbook's sheets. `dbcx status init`.
5b. Row classification (lead gate; only when a `customization-depth` or `target-readiness` handover is imported - `dbcx status next` and `dbcx discover` wait for it): `dbcx classify draft` (one candidate per unit whose disposition is in `classification.refactoring_dispositions` and per migration task -> `work/classification.json` + the skeleton `analysis/classification.md`); spawn the classification agent from `dbcx render brief classify --out` (`dbcx-agentic-loop:consolidator`, agent `consolidate-classification`; handover + requirement list only) - it proposes client-row | tech-migration | refactoring | drop and writes the product-owner texts; `dbcx md_to_json classification analysis/classification.md` (the CHECK: every candidate classified, product-owner language, named client rows exist); `dbcx classify draft` again -> `work/classification.xlsx`; the LEAD decides the class of every candidate there (dropdown) and may edit the texts; `dbcx classify approve --by <lead>`; `dbcx classify apply` (TM-nn / RF-nn rows appended to `state/requirements.json`; client-row candidates become BASELINE lines of the named rows). No classification wanted: `dbcx classify skip --reason "..."`. Rows the code analysis proposed (requirements-set extra.origin code-analysis) are decided by the client in `run.json → requirements.decisions` ({"NR-001": {"merge_into": "FR-030", "basis": "A-30"}, "NR-003": {"drop": true, "basis": "A-32"}}): a merged row is estimated inside its target (BASELINE, shown under it on Anforderungen), a dropped row only appears as an Abgrenzungen line; an undecided one is a classification candidate (client-row into ONE row, drop, or keep as its own row). A later `dbcx requirements_to_json` drops the appended rows - `dbcx classify apply` again (`status next` says so).
5c. Scope step (run.json `systems` only; automatic - nothing waits for a person, `dbcx discover` never waits for it; a run without `systems` has no scope step): `dbcx impact plan` (the pre-fill from the systems column, the interface ends and `via`, the row classes; the triage chunks - as few as `unit.context_budget` allows -> `work/impact-plan.json` and per chunk the skeleton `analysis/triage/<TRIAGE | TRIAGE-n>.md`); per chunk `dbcx render brief triage <chunk> --out` and spawn the triage agent (`dbcx-agentic-loop:consolidator`, agent `consolidate-triage[-n]`; it also reads the corpus): per row the systems it touches with one impact text each (customer language) and the reason, pre-fills kept or removed with a reason, `none` for a row that touches no system of the run, claims citing `HO-requirements-set#<row>`, `HO-landscape#<id>`, `SRC-nnn#anchor`; `dbcx md_to_json triage analysis/triage/<chunk>.md` (the CHECK); `dbcx impact apply` -> `state/impact.json` (every estimating row covered, no unknown system, an impact text per affected system), applied automatically. The triage claims then run through the normal gauntlet beside the waves (`dbcx extract_claims TRIAGE`, `dbcx render brief critic client|standard TRIAGE <n> --out`, `dbcx score_aggregate TRIAGE <n>`, STATUS `steps.TRIAGE`), followed by `dbcx impact apply` (a failed claim marks its impacts disputed; a rework: `dbcx render brief triage TRIAGE --round <n+1> --addendum <file> --out`). The dashboard view "Impact per system" shows the matrix; the lead MAY change a cell (add / remove a system, edit the impact text) - the inbox entry is applied with `dbcx inbox apply` (`dbcx impact override ...`), and once the waves are planned every change marks its work package `<row>@<system>` as new, withdrawn or re-brief for the next wave (`dbcx impact changes`). `dbcx status next` names the step before discover and the gauntlet / changes as ALSO lines.
6. Chunks and waves: `dbcx discover` (`--dry-run` first; max_chunk and light_chunk are divided by the number of options; TM / RF rows are chunked like any row, their epic is the class label) → `state/scopes.json`; `dbcx plan_waves` → `state/WAVES.json`. `dbcx status scope <name> '{"wave": n, "status": "open"}'` for every chunk; set `phases.waves.total_waves`.
6b. Several systems (run.json `systems`): the unit is the WORK PACKAGE `<row>@<system>:<option>[@<parent option>]` - every affected impact cell × every option of an agent-estimated system (a dependent system: × every parent option that is in a scenario with it, when the row touches the parent too). Systems estimated by a partner, the client or a team get none. `dbcx discover` (it never waits for the scope step: before `dbcx impact apply` the packages rest on the pre-fill) cuts chunks PER SYSTEM OPTION, as few as `unit.context_budget` allows (rows, packages, context rows and BASELINE take at most half; epics whole where they fit, small epics share a chunk, only an oversize epic is split; no division by the number of options), names `<system>-NN` / `<system>-<option>-NN`; scopes.json `wave_rule: after` makes `dbcx plan_waves` put a dependent system's chunks after every chunk of its parent. Standard critics are per system option technology (`standard-<pack>`, a `_generic` option `standard-<system>`): a chunk has the client critic and its option's critic, a triage chunk the critics of the systems its rows name (`dbcx status next` lists them).
7. Technology refresh: spawn `dbcx-agentic-loop:researcher` from `dbcx render brief research --out`; it fills `reference/platform-standard.md` for every option's technology, version and plan (every *(verify)* item resolved, section 7 only via `dbcx reference add`, rows cited as `PS-7-NNN`; vendor-code facts with the code locator as address). Skip only if section 7 already carries entries younger than 60 days for these versions - record the decision.
8. `dbcx status set phases.preflight.status '"done"'`.

## Phase 1 – Waves (one estimation analyst per chunk, every option)
Before wave 1: the rulings step (`dbcx rulings draft` -> 10-25 cross-cutting questions with options and a recommendation -> the lead answers them in one sitting -> `dbcx rulings done`, or `dbcx rulings skip`; `dbcx status next` holds wave 1 for it under `human_input.rulings: required`); under `human_input.release: batched` release the question batch at every wave gate and phase end with `dbcx questions release` after reviewing its `related` neighbours and duplicates.
For wave N (max `scoring.max_agents_per_wave` agents in parallel; wave N+1 only after wave N is closed - every scope `final`, `failed-gauntlet` or `skipped`):
1. `dbcx render brief analyst <chunk> --out` per chunk — the brief carries the OPTIONS (one TARGET block per option), the size mapping and rules, the chunk's requirement rows verbatim (with row class and options for TM / RF rows), the related requirements owned by other chunks, the BASELINE rows per requirement for EVERY option (today's shop - the real scope: coverage verdict, today, description gap, today's behaviour, units, derived requirements merged into the row, classification merges), the row-class and integration-platform rules where the run has them, for brownfield options the narrow-lookup rules, the technology notes per pack, MODEL and CLAIM CAP.
2. Spawn `dbcx-agentic-loop:analyst` agents named `analyst-<chunk>` in ONE message, each with its MODEL. Wait. Before re-spawning anything: `dbcx status inflight list` / `dbcx status verify`.
3. On report: `dbcx md_to_json estimation analysis/scopes/<chunk>.md` (once; the method rules - approach vocabulary by start, sizes, positions, no client code on greenfield rows, the lookup budget - fail the CHECK like schema errors); `dbcx status inflight done analyst-<chunk>`; `dbcx questions import <chunk>` registers the `Assumptions taken` rows as client assumptions (A-nn) and routes chunk questions. Record learnings with `dbcx learn add`.
4. Gauntlet per chunk: `dbcx extract_claims <chunk> --round <n>`; `dbcx evidence check <chunk>`; critics from `dbcx render brief critic client <chunk> <n> --out` and one per standard critic id (`dbcx status next` lists them: `standard`, or `standard-<pack>` per technology); convert each once; `dbcx score_aggregate <chunk> <n> --dry-run`, then for real. The client critic (the incumbent agency's lead developer) judges client fit and names the `ground` of every score (requirement-reading | current-shop | effort-driver | size-plausibility); a doubt about a standard statement is ground `standard-dispute` - no score: `score_aggregate` lists it under `Disputes routed` and puts the claim into the standard critic's next delta (the scope passed: send it to the standard critic as a continuation message); its answer is a reference-row correction or a note.
5. Fail → the issues file to `analyst-<chunk>`; `status: final` only when passed (or `failed-gauntlet`); wording notes → `dbcx render brief postpass <chunk> --out`.
5b. Architect step (run.json `systems` only; automatic - nothing waits for a person): in a multi-system run every work package carries starting_point, coverage (standard needs a PS-7 reference - the CHECK downgrades an unreferenced one to extension, confidence low, and says so) and confidence; a requirement the system cannot carry is a gap (gap_reason, optional route_suggestion, the own share sized). When a wave is closed and its analysts reported gaps, `dbcx status next` names the step: `dbcx architect plan` (one batch ARCHITECT-n over all open gaps -> `work/architect-plan.json` + the skeleton `analysis/architect/ARCHITECT-n.md`); spawn the architect from `dbcx render brief architect ARCHITECT-n --out` (`dbcx-agentic-loop:consolidator`, agent `consolidate-architect-n`; corpus, landscape, impact matrix, the gap rows): per gap overrule | route-estimated | route-landscape | reduce-to-standard, the latter two with a client assumption; `dbcx md_to_json architect analysis/architect/ARCHITECT-n.md` (the CHECK); `dbcx architect apply` -> `state/architect.json` with the follow-up work packages (`dbcx architect changes`) for the next wave (`dbcx discover --pickup`, step 8); `dbcx questions import ARCHITECT-n` registers the assumptions (A-nn). Its claims run through the gauntlet like the triage's (`dbcx extract_claims ARCHITECT-n`, critics, `dbcx score_aggregate ARCHITECT-n <n>`, then `dbcx architect apply`). A row's second visit gets a final decision - no third routing. The dashboard view "Gap decisions" shows them; an override there is optional (`dbcx inbox apply` -> `dbcx architect override`).
6. After wave 1: measure the brownfield lookups (share of brownfield rows with a lookup, how often a lookup moved a size - `size_before_lookup` vs `size`) and record the decision whether the client repository stays open for later waves (`dbcx status assume ...`).
7. After the first chunks are final: `dbcx build_excel D1 --interim` (team checkpoint) and one gate persona reads it early.
8. Several systems: the analyst brief of a chunk carries ONE system option, its WORK PACKAGES (req_id + the `option` value to write - `<option>` or `<option>@<parent option>`; claims target `D1/Schaetzung#<req_id>@<option value>`), the impact text in this system and the row's impacts in the other systems, the CONTEXT ROWS (reference rows the rows name, rows linked by roll-up with their impacts; the REMAINDER RULE: a row others roll up to names them in its estimation assumption and sizes only what it covers beyond them - the CHECK refuses it otherwise), and for a dependent system THE PARENT'S APPROACH per row and parent option from the parent's passed analyses. The CHECK refuses a row that is no active work package of the chunk. At every wave gate: work-package changes of the impact matrix (dashboard overrides, a triage rework; `dbcx impact changes` shows them with their packages) and the architect's follow-ups (`dbcx architect changes`) → `dbcx discover --pickup`: new → follow-up chunks in the first wave that has not started, withdrawn → the package is marked and its row dropped, re-brief → re-estimated in a follow-up chunk (or updated in place while its chunk has not started; the architect's note goes on the package); an architect's external or landscape cell is an input cell of the workbook, no chunk; a re-briefed or withdrawn package re-briefs / withdraws the packages of its dependent systems for the same row (cascade; they move behind a parent package that is re-estimated); the changes are marked picked up. Then `dbcx plan_waves` and register the follow-up chunks (`dbcx status next` names unregistered ones). Nothing waits for a person.

## Phase 2 – Consolidation (SUMMARY)
1. Every chunk `final` or `failed-gauntlet`. `dbcx render digest SUMMARY` — every estimation row with its citing claims, the mechanisms whose size diverges per option, the requirements an option has no row for.
2. Spawn `dbcx-agentic-loop:consolidator` from `dbcx render brief consolidate SUMMARY --out`: totals per option / epic / release (and per scenario), calibration per option (every changed row id listed), fixed phases per option - per SCENARIO when the run declares scenarios, starting from the FIXED PHASE SEEDS (keep / adjust / drop each in `Fixed phase seeds`) - incl. the technical migration tasks without a requirement that no TM row carries, the exclusions register, qualitative risks. Convert once: `dbcx md_to_json summary analysis/consolidated/SUMMARY.md`.
3. Gauntlet SUMMARY. Put the `rows_changed` ids into the critic briefs by hand.
4. Passed → write `analysis/summaries/D1.md` (deliverable language, no typed-in numbers - `{kpi:total_<option>}`, `{kpi:cost_<option>}`, `{kpi:dev_<option>}`, `{kpi:req_total}`; with scenarios `{kpi:total_<scenario>}`, `{kpi:cost_<scenario>}`, `{kpi:platform_<scenario>}`, `{kpi:is_<scenario>}`): the total per option or scenario, what drives the difference, which assumptions move the totals, which requirements need a decision.

## Phase 3 – Build the workbook (orchestrator)
1. `dbcx build_excel D1` (add `--internal` for the team's review notes). The build runs `dbcx lint_deliverable` and rejects process language - fix the analyses, never the workbook.
2. Check with openpyxl: every sheet present; the band headers of Schaetzung name every option; no `NICHT BEWERTET`; `Summen` and `Vergleich` show every option (with scenarios: `Szenarien`, `Summen`, `Vergleich` every scenario); change one size, a surcharge, a fixed phase and the day rate in a copy and see every total follow; no `path:line` or file name in any cell of either edition; `Aussagen` carries a score per applicable critic; no formula points at a missing sheet. `dbcx lint_deliverable --standalone --all` clean. `dbcx status set phases.excel_build.status '"done"'`.

## Phase 4 – Final gate
1. Spawn `dbcx-agentic-loop:gate-persona` once per persona in `scoring.gate_personas` (cto, head_of_ecommerce, product_owner, cfo; the product owner also asks whether each option includes what today's shop does beyond the written requirement) and the verifier (it samples rows of every option and checks the size against its basis - requirement text, code-analysis row, reference row, assumption; no repository reading, no code stratum). Convert each, `dbcx gate_aggregate <round>`.
2. Fail → blockers first: texts in `overrides/deliverables.{languages.deliverable}.json`, README, Management_Summary, Parameter wording; provability → the owning analyst or the consolidator adds evidence (mini gauntlet round). Rebuild, re-run the failed personas plus one that passed. Max `scoring.max_gate_rounds` rounds.

## Phase 5 – Report and release
`docs/FINAL_REPORT.md` (English; real numbers: rounds and scores per chunk, failed chunks, gate scores, the lookup measurement, open assumptions, what the estimate does NOT contain). `dbcx handover export fit-estimation`; `dbcx handover export client-assumptions` when the client should confirm the readings in a later run. `dbcx learn export` (on the user's word; with several technology packs each verified fact goes with the pack it is attributed to). Tell the user where everything is; never claim a pass that did not happen.

## Guard rails
- One chunk per agent, every option in the same file. Requirements of another chunk are not estimated - they are an `Open questions` row to that chunk.
- Nothing aggregated is typed into Excel: only `dbcx build_excel` writes the workbook. Size mapping, surcharges, sprint limit and day rate live on the Parameter sheet; the fixed phases are the only typed person days, editable on Zuschlaege_und_Phasen.
- No question to the client for an unclear requirement: the most probable reading is taken and registered as an assumption the client confirms or denies.
- Nothing is above {last:estimation.sizes}; a larger requirement is cut into estimation positions. Requirement rows at or above the sprint limit are flagged.
- No double counting: work a surcharge or fixed phase carries is size 0 on the row, and the row names the block.
- Brownfield rows rest on the handover; a code lookup is narrow (named question, budgeted classes and extensions) and recorded on the row - its classes stay in the analysis and the client critic's pack, never in a workbook. Greenfield rows never cite the client repository; both options size the real scope of a requirement (text + description gap + today's behaviour).
- Product-owner language: WHAT is used or built, never HOW in code - the CHECK refuses file names, paths, line numbers, packages, class names and the run's unit names in every text field, the hygiene layer in every text column of the customer edition.
- A refactoring row (RF) exists for brownfield options only; a technical migration row (TM) for every option it applies to; one interface change is carried by one row.
- Vendor standard code is evidence through reference rows only - never copied into a deliverable, never sent to an external service.
- Real numbers, failed rounds and open issues are reported. Scores are never edited by hand.
- Client-facing text speaks about the requirements and the options: no rounds, corrections, reviewers, sessions or edit dates in any cell.
- No client requirement text, client name or chunk name reaches an external service. Do not run: {list:rules.do_not_run}.
- Delegation budget: spawn only what this plan names; critics persist per scope (rounds are messages); agents spawn helpers on the HELPER MODEL only.
