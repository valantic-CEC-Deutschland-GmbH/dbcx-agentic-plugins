# Orchestration plan – {engagement.client}: technology shortlist with strategic scoring

Trigger: the user says **"Execute the plan"** after (a) `dbcx check_fill` reports 0 placeholders, (b) `dbcx smoke tech-scoring` ends with SMOKE TEST OK, (c) the client material is in `input/` (and indexed with `dbcx corpus index`), (d) `run.json` names the technologies to evaluate. Run everything below without asking questions; decisions go to `state/STATUS.json` → `assumptions[]` (`dbcx status assume ...`). Resume point after any interruption or context compaction: `dbcx status verify`, then `dbcx status next` (status-driven; the SessionStart hook prints verify automatically). "How far are we?" at any time → `dbcx progress` and the progress-reporter. Feedback given in chat during the run → `dbcx status feedback add "..."` immediately.

Plugin: `{plugin}` (tools `dbcx <tool>` or `python3 {tools}/<tool>.py`; roles are the plugin agents `dbcx-agentic-loop:<role>`). Every agent is spawned from a brief FILE: `dbcx render brief ... --out [--addendum <file>]` writes `analysis/briefs/<agent>[-rN].md` and prints path, MODEL and agent name; the prompt references that path (the spawn hook checks path and model and registers the agent in `in_flight`). Rounds ≥ 2 need `--addendum <file>` (or `--no-addendum`). Reviewers stay alive per scope: later rounds are SendMessage calls with the new delta, not new spawns.

Decision this run supports: **{decision.question}** – timeline **{decision.timeline}**. Guardrails: **{decision.guardrails}**. Shortlist size **{shortlist.size}**; score scale 0–{scale.max} with guardrail floor {scale.guardrail_floor}. Deliverable in `{languages.deliverable}`; chat and agent reports English.

| | Deliverable | Built by (orchestrator only) | From |
|---|---|---|---|
| D1 | `deliverables/{deliverables.D1.file}` | `dbcx build_excel D1` | `analysis/scopes/*.md` (one per technology) + `analysis/consolidated/SHORTLIST.md` |

One scope = one technology (`T-01`, `T-02`, … – the short code keeps vendor names usable in web queries; the technology name travels in the brief and in every table). All technologies run in parallel (`wave_rule: parallel`, at most `scoring.max_agents_per_wave` agents at a time).

## Phase 0 – Preflight (orchestrator)
1. `dbcx check_fill` → 0. `dbcx smoke tech-scoring` → SMOKE TEST OK. `dbcx md_to_json --generate` (templates/schemas current).
2. Client side: `dbcx corpus index` over the handed-over material (strategy papers, workshop notes, landscape diagrams, the requirement list) so every client statement has a locator `SRC-nnn#anchor`. Requirements: `dbcx requirements_to_json` (client workbook + `requirements_mapping.json`) or `dbcx handover import requirements-set` from a released `requirements` run. `dbcx intake` – every defect of the imported material becomes a CLIENT question, not a review finding.
3. Criteria and weights: check `criteria` in the merged configuration (`dbcx render context analyst T-01` prints the CRITERIA block the analysts will see). Adjust ids, names, weights and the `guardrail` flags in `run.json` for this client's decision – the weights are also editable in the finished workbook, but the criteria SET must be fixed before the analysts start, because every technology is scored against the same rows. Record any change as an assumption.
4. `dbcx status init`; `dbcx discover` (one scope per technology, prints the T-nn → technology mapping); `dbcx plan_waves`; `dbcx status scope <id> '{"wave": 1, "status": "open"}'` for every scope; set `phases.waves.total_waves`.
5. Technology research: spawn `dbcx-agentic-loop:researcher` with `dbcx render brief research --out`; it fills `reference/platform-standard.md` (every *(verify)* item of the packs resolved with URL and date; section 7 only via `dbcx reference add`, rows carry ids `PS-7-NNN` – the analysts cite by id instead of searching the same pages again). Skip only if section 7 already holds dated rows for these versions or plans, and record the decision as an assumption.
6. `dbcx status set phases.preflight.status '"done"'`; log; record assumptions.

## Phase 1 – Waves: one scoring per technology
Before wave 1: the rulings step (`dbcx rulings draft` -> 10-25 cross-cutting questions with options and a recommendation -> the lead answers them in one sitting -> `dbcx rulings done`, or `dbcx rulings skip`; `dbcx status next` holds wave 1 for it under `human_input.rulings: required`); under `human_input.release: batched` release the question batch at every wave gate and phase end with `dbcx questions release` after reviewing its `related` neighbours and duplicates.
For each wave (max `scoring.max_agents_per_wave` agents in parallel; wave N+1 is rendered and spawned only after wave N is closed - every scope `final`, `failed-gauntlet` or `skipped`. Overlapping waves multiply the live agents (one analyst plus the client critic and every standard critic per scope in gauntlet) and have run a session out of budget mid-round; `dbcx render brief analyst` refuses a scope of a later wave, `--force` plus a logged `dbcx status assume <reason>` is the only way past it):
1. `dbcx render brief analyst <T-nn> --out` per technology (the brief carries MODEL, CLAIM CAP, the CRITERIA block, the CLIENT GUARDRAILS block, the requirement counts, the TECHNOLOGY KNOWLEDGE block with that technology's pack paths, routed open questions and a resume note).
2. Spawn `dbcx-agentic-loop:analyst` agents named `analyst-<T-nn>` in one message, each with its MODEL. Wait. Before re-spawning anything: `dbcx status inflight list` / `dbcx status verify` – output on disk = delivered.
3. On report: `dbcx md_to_json scoring analysis/scopes/<T-nn>.md` (once; read the WARNING lines); `dbcx status inflight done analyst-<T-nn>`; open questions → `dbcx questions import <scope>` (registers the analyst's Open questions rows with their proposed answers; `dbcx questions add` for questions of your own), later `answer|scored|forward` (`to = client` questions become the workbook's Open_Questions sheet). Record learnings with `dbcx learn add`.
4. Gauntlet per technology as soon as the draft converts OK: `dbcx extract_claims <T-nn> --round <n>`; `dbcx evidence check <T-nn>` (dangling locators are the client reviewer's first stop); reviewers from `dbcx render brief critic client <T-nn> <n> --out` and `... standard <T-nn> <n> --out` (round 1) or SendMessage with the new delta (round ≥ 2; brief with `--addendum`); convert each once; `dbcx score_aggregate <T-nn> <n> --dry-run`, then for real. On fail SendMessage the issues file to `analyst-<T-nn>` (re-spawn with `dbcx render brief analyst <T-nn> --round <n> --addendum <file> --out` only if the agent is gone). `status: final` only when passed (or `failed-gauntlet` after the last round); wording notes on passing claims → `dbcx render brief postpass <T-nn> --out`.
5. Completeness gate before Phase 2: every final analysis has one score row per criterion id (the digest's Completeness section lists the misses) and every capability row names a locator. A technology whose analysis failed its gauntlet still enters the ranking – with its open issues named in the consolidation.

## Phase 2 – Consolidation: calibration, ranking, shortlist
1. All technology analyses final or failed-gauntlet. `dbcx render digest SHORTLIST` (score matrix across all technologies, completeness check, capability rows without a source, reported guardrail hits – the consolidator reads this, not N raw analyses).
2. Spawn one `dbcx-agentic-loop:consolidator` from `dbcx render brief consolidate SHORTLIST --out`. It calibrates (comparable rationale → comparable score, every change a `Calibration` row by id), ranks, shortlists `{shortlist.size}`, writes the fit statements and the partner-friendly explanations and fills the guardrail table. Convert once: `dbcx md_to_json shortlist analysis/consolidated/SHORTLIST.md`.
3. Calibration changes table rows, and changed table rows are invisible to the claims register: put the row ids the consolidator reports into the reviewers' brief by hand (the coverage report shows which rows no claim cites).
4. Gauntlet SHORTLIST with both reviewers (the standard reviewer on `models.critic_standard_consolidation`): `dbcx extract_claims SHORTLIST --round <n>`, briefs, convert once each, `dbcx score_aggregate SHORTLIST <n>`.

## Phase 3 – Build the deliverable (orchestrator)
1. Write `analysis/summaries/D1.md` (deliverable language, no typed-in numbers, only passed claims, no process language): the decision, the shortlist with one sentence per technology, the guardrail picture, what the client must still answer.
2. `dbcx build_excel D1` (+ `--internal` for the team's review-notes workbook, `--all --interim` for a checkpoint during Phase 1). The build runs `dbcx lint_deliverable` and rejects process language – fix the analyses (postpass briefs), never the workbook.
3. Check with openpyxl: every sheet present; the Ranking chart present; the internal review workbook (`dbcx build_excel D1 --internal` → `work/internal/Technology_Scoring_Review_Notes.xlsx`) shows no `CHECK` in the Shortlist and Scores check columns (a CHECK means the consolidator's rank or an analyst's guardrail flag contradicts the workbook's own calculation – settle it in the analysis, never in the sheet; the customer edition shows only the calculated rank and flag); `Capabilities` has no row without a source; `Claims` carries scores for every claim; no formula references a missing sheet. Then change one weight on `Parameters` and confirm that the totals and the ranking move – that is the sheet's whole purpose in the decision meeting. `dbcx status set phases.excel_build.status '"done"'`.

## Phase 4 – Final gate
1. Spawn `dbcx-agentic-loop:gate-persona` once per persona in `scoring.gate_personas` in parallel (`dbcx render brief gate <persona> <round> --out`). Convert each (`dbcx md_to_json gate ...`), `dbcx gate_aggregate <round>`.
2. Fail → blockers first: understandability/actionability → `overrides/deliverables.{languages.deliverable}.json` texts, README, Management_Summary, column order; provability → the owning analyst or the consolidator adds evidence (mini round on the changed claims). Rebuild, rerun the failed personas plus one that passed. Max `scoring.max_gate_rounds` rounds.

## Phase 5 – Report and handover
`docs/FINAL_REPORT.md` (English; real numbers: rounds and final averages per technology, failed scopes, gate scores per persona × dimension, open issues, assumptions, and the questions the client still owes). `dbcx handover export shortlist` releases the shortlist for a following `tech-fit-estimation` run on the shortlisted technologies. `dbcx learn export` (on the user's word) so the facts verified here and the learnings reach the plugin maintainer. Tell the user where everything is; never claim a pass that did not happen.

## Guard rails
- One technology per agent. An analyst never opens another technology's analysis and never compares technologies – the comparison is the consolidation's and is reviewed as such.
- The two reviewers have disjoint evidence bases (hook-enforced): the client reviewer sees the client's context and no vendor documentation, the standard reviewer sees the vendor documentation and nothing of the client. A dispute between them about a product fact is settled by the standard reviewer, about a client fact by the client reviewer.
- No client name, no scope name, no client locator in any web query. Web lookups are generic product questions only.
- Every criterion score is an assessment claim with a client locator AND a vendor locator; every capability is a fact claim with the version or plan it holds for. A capability without a locator is `unknown`, never `yes`.
- The criteria set is fixed before the analysts start; the weights stay editable to the end (they are a client decision, not ours).
- Nothing aggregated is typed into the workbook: weighted totals, ranks and shortlist flags are formulas, and the assessed rank sits next to the calculated one with a CHECK column.
- Partner-friendly wording throughout: context-specific limitations, no absolute criticism of any product, nothing that would embarrass anyone if the vendor read it.
- Scores are never edited by hand (`build_excel` verifies the checksums written by `score_aggregate`). Real numbers, failed rounds and open issues are reported.
- Client-facing text speaks about the client's decision and the technologies: no rounds, corrections, reviewers, sessions or edit dates in any cell (`dbcx lint_deliverable`).
