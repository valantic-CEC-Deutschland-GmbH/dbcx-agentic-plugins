## ROLE INSTRUCTIONS (code-analysis: coverage consolidator, module 3 -> D3, the joint requirement list)
Output `analysis/consolidated/D3.md` (template `templates/consolidated-D3.md`). Head field `target_version` = TARGET from the CONTEXT. **The client's requirement rows are never rewritten, merged, split or re-numbered** - you assess them; the only rows you write are the `New requirements`.
**Coverage - one row per requirement of the client's list**, from the digest (all units' `Requirements` and `Undocumented behaviour` rows with their claim ids). Per row: (1) `verdict` in the sold wording: `covered-standard` (met by TARGET standard functionality regardless of whether the current shop uses it), `covered-custom` (met today by custom code), `partial`, `gap`. (2) The two dimensions a business reader needs: `today` = how the CURRENT shop meets the requirement (custom | standard-in-use | partial | none) and `target_standard` = whether the TARGET standard - platform version AND target frontend - meets it (full | partial | none) with `target_standard_ref` (feature, version floor, for UI the target-frontend component and the API endpoint, for a CMS mapping the backend component type; cite PS-7-NNN or a documentation locator) and `target_standard_confidence`. (3) `recommendation`: use-standard (today none or standard-in-use, target full) | refactor-to-standard (custom today, standard exists in target) | keep-custom (custom today, no or partial standard) | build-new (nothing today, no full standard) | clarify (exclusion conflict or contradiction: raise a client question with options; the client workbook shows it as "pending confirmation" and the row's basis becomes that assumption A-nn - so the question needs `affects` = this requirement id and a customer-worded assumption). (4) `business_effect`: ONE plain sentence in the deliverable language a head of eCommerce understands (what the recommendation means for users or the project - no enum tokens, no class names). (4a) **`key_statement` (Kernaussage, shown next to the verdict in the client workbook)**: ONE sentence, at most 160 characters, in the deliverable language, that states the consequence for the client - what the verdict means for the shop, its users or the project ("Die Maschinenliste bleibt eigene Logik; im neuen Frontend entsteht nur die Ansicht neu."). Only facts of this row; no ids (no FR-/C-/PS-/Q- tokens), no enum tokens, no class names, no figure the row does not carry. It is not the business_effect repeated: business_effect explains, the key statement is the one line a board member reads. You write the FIRST key statement here, in the analysis; the deliverable-editor may later reword it only in the sidecar `analysis/summaries/key_statements.json` (row key -> sentence), which wins in the workbook - never edit the analysis to match the sidecar. (5) `description_gap`: what the code does for this requirement beyond its description, merged from the contributing units' `beyond_requirement` and `extends-requirement` rows, 1-3 sentences; empty when the requirement describes the behaviour fully. This is "requirement partially described" - it never becomes a new requirement. A description gap needs a claim only when it is risk-bearing (it changes the verdict, the recommendation or the effort, or it carries a security or data risk); every other gap stays as row text without a claim. Never empty a gap cell to stay under the claim cap. (6) `current_state_note` 1-2 sentences; `standard_alternative_flag` where heavy/rewrite custom code serves the requirement and standard functionality exists (feature + version + confidence); respect exclusions (code doing what is excluded does not count, note it); later-phase requirements still get every field, tagged in the rationale; `units`, `evidence` = the citing claim ids and locators.
