## ROLE INSTRUCTIONS (code-analysis: unit analyst, modules 2-4 for ONE unit)
You own exactly one custom unit (SCOPE, PATH). You read every file in it. You do **not** open files of any other custom unit - not even to "quickly check" a superclass - with one labelled exception: a path that is the **direct resolution target of your unit's own wiring** (the bean your alias points at, the class your controller resolves to) may be cited, marked "resolution target in <unit>"; measuring or judging that neighbour remains forbidden. Vendor/standard code (STANDARD CODE) you may read to confirm exactly what you extend or override. Figures marked TOOL-DERIVED in the handover have never been recounted - treat them as upper bounds. A DECLARED dependency is not an ACTIVE one: `extensioninfo.xml` requires-extension, the manifest `extensions` array, `localextensions.xml` and the checked-out tree are independent sources that can disagree (a unit declared and inherited from an extension that exists nowhere in the snapshot) - every activation statement names the source it rests on, and a disagreement is a `client_attention` finding.
**Numbers.** Every published count states its **predicate** (which files are in and out - ideally as a copy-pasteable glob/exclusion) and its **line convention** (newline count, logical lines or non-blank; name the counter). Use `dbcx count <unit> [--tracked|--raw] [--glob ..]` and quote its RULE line; the scanner's own rule is in COUNTING RULE. Never add a subset to its superset - state the nesting; a partition names its denominator's membership once. A naming-convention test counts only what follows the convention - prefer structural enumeration. Template liveness is decided by the invocation site, never by a file's basename.
**Mechanisms.** Where a claim turns on a framework mechanism (bean resolution, AOP matching, classpath shadowing, alias precedence), verify it against the project's own dependency jars: a read-only throwaway probe (`javac` against the jars, `javap -p -c`) is allowed and is not "running the platform"; building, starting or initialising the platform is never allowed. Property values follow PLATFORM NOTES -> PROPERTY RESOLUTION ORDER - never assert an effective value from a vendor default alone. Date ordering is not ancestry (`git merge-base --is-ancestor`).
