Trigger: the user says **"Execute the plan"** after (a) `dbcx check_fill` reports 0 placeholders, (b) `dbcx smoke` ends with SMOKE TEST OK, (c) the client repository is checked out read-only at `{repo.path}`. Run everything below without asking questions; decisions go to `state/STATUS.json` → `assumptions[]` (`dbcx status assume ...`). "How far are we?" at any time → the `progress` sub-command of the skill (no fixed cadence). Feedback given in chat during the run → `dbcx status feedback add "..."` immediately.

Plugin: `{plugin}` (tools `dbcx <tool>` or `python3 {tools}/<tool>.py`; roles are the plugin agents `dbcx-agentic-loop:<role>`; scoring `docs/SCORING.md` in the plugin). Orchestrator session: use the semantic orchestrator profile. Deliverables speak about the shop only – no rounds, corrections or reviewers in any cell (`dbcx lint_deliverable` guards it).

## Phase 0 – Preflight (orchestrator)
1. `dbcx check_fill` → 0. `dbcx smoke` → SMOKE TEST OK. `dbcx md_to_json --generate` (templates/schemas current).
2. Repository sanity: unit manifests below `{list:unit.repo_roots}`, vendor code below `{list:unit.standard_dirs}`, version markers and active-unit config per the pack notes (`dbcx render context inventory` shows them). Record in STATUS `repo.*`.
3. `dbcx requirements_to_json` (compare the count with the client's list; without a client list the requirements are AS-IS and are written from the unit analysts' `Requirements`/`Target API features` rows plus D1 before Phase 3 – no separate repository-wide extraction). `dbcx status init`.
4. Version-pair refresh: spawn `dbcx-agentic-loop:researcher` with `dbcx render research`; it updates `reference/platform-standard.md` (every *(verify)* item resolved or marked unverifiable with reason; section 7 written only via `dbcx reference add|correct`, rows carry ids `PS-7-NNN` – cite by id). Skip only if the reference file has a section-7 entry newer than 60 days for this version pair; record the decision as assumption.
5. Deliverable-first check (A1) before any analysis: build a mock customer edition - `dbcx smoke code-analysis <abs tmpdir> {languages.deliverable}` (outside the run folder) writes the fixture workbooks with this method's spec; copy the run's `overrides/deliverables.{languages.deliverable}.json` and `overrides/labels.{languages.deliverable}.json` into `<tmpdir>/code-generic/overrides/`, rebuild there (`DBCX_RUN=<tmpdir>/code-generic dbcx build_excel --all`) and render (`dbcx render_workbook --all` in the same folder). The lead and one gate persona (the least technical; its key questions from `dbcx gate questions <persona>`) read the rendered customer edition: can every key question be answered from these sheets, columns, tiles and charts? Missing columns, KPIs, charts or wording become id-keyed run `patches` in `overrides/deliverables.{languages.deliverable}.json` (`dbcx build_excel --check --all` = 0 errors), fields the deliverable needs but the analysis templates lack go to the lead as a method gap. Then the deliverable spec is frozen: `dbcx status assume "deliverable spec frozen: <patch summary>"`; later changes only through a gate fix plan.
6. `dbcx status set phases.preflight.status '"done"'`; log; record assumptions.

## Phase 1 – Module 1 inventory → D1
1. `dbcx scan_inventory {repo.path}` (add the platform path as a second root when the vendor code is checked out elsewhere) → `analysis/inventory/inventory.json` (raw + git-tracked metrics, the counting rule as text, per-unit deprecation hits with kind) + `deprecation_hits_per_unit.md` + `scan_log.txt` (+ `state/derived_knowledge.json`). Sanity-check unit count, categories, unknown dependencies (add to `overrides/knowledge.json standard_units` and re-scan if vendor units are unknown).
2. Spawn `dbcx-agentic-loop:inventory-analyst` from `dbcx render brief inventory --out`. Convert once: `dbcx md_to_json inventory analysis/inventory/inventory_analysis.md`; on WARNING/INVALID send the output back. The `activation` column (active | dead | stub) must be filled for every unit.
3. Gauntlet D1: `dbcx extract_claims D1 --round <n>`; spawn `critic-client` and `critic-standard` from `dbcx render brief critic client D1 <n> --out` / `... standard D1 <n> --out` (round 1) or SendMessage the new delta to the running critics (round ≥ 2, brief with `--addendum`); convert each once; `dbcx score_aggregate D1 <n> --dry-run`, then for real. Read the issues file (blocking verdicts, divergence, notes on passing claims). Fail → issues file to the analyst (SendMessage), next round (max `scoring.max_gauntlet_rounds`; rounds > `freeze_register_after_round` add nothing). Passed → `dbcx render handover`; post-pass wording notes → `dbcx render brief postpass D1 --out`.
4. `dbcx plan_waves` → `state/WAVES.json` (reads D1 `activation`: dead → light pass, stub → skipped); review (core first; a large frontend unit as early as its dependencies allow); `dbcx status scope <name> '{{"wave": n, "status": "open"}}'` for every unit; set `phases.waves.total_waves`. Overrides only via `--light/--skip` + assumption.
5. `dbcx build_excel D1` (no management summary yet - the deliverable-editor writes it after the final build, Phase 5 step 0); `dbcx build_dependency_diagram --png` (`--include-standard` when ≤ 25 custom units). Spawn one gate persona (the least technical) on D1 for an early read; queue its presentational issues.

## Phase 2 – Waves (modules 2-4 per unit)
Before wave 1: the rulings step (`dbcx rulings draft` -> 10-25 cross-cutting questions with options and a recommendation -> the lead answers them in one sitting -> `dbcx rulings done`, or `dbcx rulings skip`; `dbcx status next` holds wave 1 for it under `human_input.rulings: required`); under `human_input.release: batched` release the question batch at every wave gate and phase end with `dbcx questions release` after reviewing its `related` neighbours and duplicates.
For wave N (max `scoring.max_agents_per_wave` agents in parallel; wave N+1 is rendered and spawned only after wave N is closed):
1. `dbcx render brief analyst <name> --out` per unit (context incl. MODEL and CLAIM CAP, COUNTING RULE, DEPRECATION HITS, note blocks, D1 handover section with scanner-derived marks, routed open questions, resume note).
2. Spawn `dbcx-agentic-loop:analyst` agents named `unit-<name>` in one message, each with its MODEL (light-pass units on `models.analyst_light`). Wait. Before re-spawning anything: `dbcx status inflight list` / `dbcx status verify` – output on disk = delivered.
3. On report: `dbcx md_to_json unit analysis/units/<name>.md` (once; read WARNINGs); `dbcx status inflight done unit-<name>`; open questions → `dbcx questions import <scope>` (registers the analyst's Open questions rows with their proposed answers; `dbcx questions add` for questions of your own), later `answer|scored|forward` (forward only from a passed round, with qualification; asker already passed → post-pass text correction). Record the agent's learnings with `dbcx learn add`.
4. Gauntlet per unit as soon as the draft converts OK: `dbcx extract_claims <name> --round <n>`; critics from `dbcx render brief critic <critic> <name> <n> --out` (round 1) or SendMessage with the new delta (round ≥ 2; brief with `--addendum`); convert once each; `dbcx score_aggregate <name> <n> --dry-run`, then for real. Light-pass units: light gauntlet (balanced_review client critic, `max_gauntlet_rounds_light`). On fail SendMessage points `unit-<name>` at `analysis/gauntlet/<name>/round<n>-issues.md` - the path, never a restatement of its issues (re-spawn with `dbcx render brief analyst <name> --round <n> --addendum <file> --out` only if gone). `status: final` only when passed (or `failed-gauntlet` after the last round); a thin pass with a long issues list may get another round while the register is open (`passed-rework-ordered`, assumption logged); wording notes → `postpass` brief, then `dbcx postpass check <name>` (refusal → back to the corrector with its reason; `--accept <ids>` only with a logged `dbcx status assume`).
5. Corrections of public facts (service names, types, feature ownership) are forwarded to dependents; a corrected figure gets `dbcx grep_scopes` before and after.
6. Wave N is closed when every one of its scopes is `final`, `failed-gauntlet` or `skipped`; only then is wave N+1 rendered and spawned - never while a wave-N scope is still analysing, in gauntlet or in rework. Dependencies being final is necessary, not sufficient. Overlapping waves multiply the live agents (one analyst plus the client critic and every standard critic per scope in gauntlet) and have run a session out of budget mid-round, killing agents before they could finish. `dbcx render brief analyst` refuses a scope whose wave is not the open one; `--force` plus a logged `dbcx status assume <reason>` is the only way past it. Persist `phases.waves.current_wave`. After D2 is first built (`dbcx build_excel D2` or `--interim`), one gate persona reads it early.

## Phase 3 – Consolidation (D3, D4)
1. All unit analyses final/failed-gauntlet. `dbcx build_excel D2` as orientation. `dbcx render digest D3` and `dbcx render digest D4` (all unit rows with citing claim ids and provenance – the consolidators read these, not the raw analyses).
2. Spawn `consolidator` and `consolidator` in parallel from `dbcx render brief consolidate D3|D4 --out`. Convert once. Open questions → owning `unit-<name>` (respawn with its context if gone). Follow-ups to a running consolidator go as ONE message; never extract while it is running (`extract_claims` refuses).
3. Gauntlet D3 and D4 (client and standard critics, kept alive across rounds, Opus platform critic). Put the table rows the consolidator reports as changed into the critic brief – the coverage report shows rows no claim cites.

## Phase 4 – Build deliverables (orchestrator)
1. No management summary is written here: the `deliverable-editor` writes `analysis/summaries/D1..D4.md` AFTER the build with live `{kpi:<id>}` values (Phase 5 step 0), and Kernaussagen it rewords go to `analysis/summaries/key_statements.json` (`{"<row key>": "<sentence>"}`, it wins over the analysis field). `dbcx d0 collect` and curate `analysis/consolidated/D0.json` (severity high | medium | low, `consequence` for the client, recommendation, what settles an open row, passed claim ids): a curated row overrides finding / severity / recommendation / consequence of its row on the D2 sheet Sicherheit_und_Betrieb (built by default) and goes into the final report; the D0 workbook is built only if enabled.
2. `dbcx export_artefacts` (writes `analysis/consolidated/D2.json` = customization-depth and `analysis/consolidated/requirements_set.json` = the joint requirement list: the client's rows verbatim + the NR rows of D3 - both are released later by `dbcx handover export`). `dbcx build_excel --check --all` (0 errors: ids, placeholders, at most two decision columns per sheet, dataset fields), `dbcx build_excel --all` (customer edition in `deliverables/`, full edition with Aussagen and Offene_Fragen in `deliverables/intern/`; + `--internal` for the team's review workbook with the formula / check / confidence columns) and `dbcx build_dependency_diagram --png`. The build runs `dbcx lint_deliverable` and rejects process language – fix the analyses (postpass briefs), never the workbook. Check with openpyxl: every sheet present, Overview charts present, the full edition's Aussagen has scores for all claims, no formula references a missing sheet, no NOT-ASSESSED in D3, the D3 requirement sheet carries the client's text columns and the frontend roll-up, the new-requirements sheet and the compact feature sheet are present, D4 has the feature sheet keyed by primary requirement, the interface sheet and the migration-tasks sheet (no blockers sheet), every D2 row with a disposition. `dbcx md_to_json` printed no atomic-claim WARNING for a final scope (over-long / multi-figure / multi-target claims). `dbcx status set phases.excel_build.status '"done"'`.

## Phase 5 – Final gate (customer edition; three layers, `docs/SCORING.md` §3 in the plugin)
The gate reads only what the client's readers receive: the customer workbooks at the top of `deliverables/` and their renderings - never `deliverables/intern/`, the analyses or `work/` (engine evidence bases, hook-enforced). Max `scoring.max_gate_rounds` rounds; `dbcx status next` prints each step.
0. Pre-gate: `dbcx build_excel --all` (customer + full edition) → `dbcx render_workbook --all` (Excel: cached values, PDF + page PNGs in `work/render/<date>/<D>/`) → `dbcx lint_deliverable --standalone --all --round 1`. `dbcx render brief editor 0 --out` → `deliverable-editor` writes `analysis/summaries/D1..D4.md` after the build (every figure a `{kpi:<id>}`; Kernaussagen, top assumptions, next steps), clears the hygiene findings through run overrides / labels, rebuilds, renders and re-runs the hygiene layer until it is clean. The key questions (`dbcx gate questions`) were tailored at `prepare` and signed off by the lead.
1. Round n: in one message, one `gate-persona` per persona in `scoring.gate_personas` (`dbcx render brief gate <persona> <n> --out`: the persona's key questions and only the workbooks they name - CTO D1/D2/D4, head of IT D1/D2/D4, head of eCommerce D3/D4, head of marketing D4/D3/D2, product owner D3/D4, the Annahmen sheet in each) and the `gate-verifier` (`dbcx render brief verifier <n> --out`: ~15 tool-drawn rows per workbook checked against the repository). Both briefs refuse while the hygiene layer fails. Convert each once (`dbcx md_to_json gate|verifier …`).
2. `dbcx gate_aggregate <n>`: pass = hygiene clean, verifier >= 8 on every workbook, per persona mean >= 8, no key question < 7, no blocker, no major without a lead decision. It writes `analysis/gate/round<n>-fixplan.md` (clusters with mechanism, owner, acceptance test, "unchanged since round k") and suggested `dbcx learn add` lines for the non-content clusters - record them.
3. FAIL → `dbcx render brief editor <n> --out` → `deliverable-editor` executes the fix plan: spec/override (id-keyed `patches` in `overrides/deliverables.de.json`: columns, KPIs, tiles, charts, overview blocks, Plattform labels), labels, summaries and Kernaussagen (sidecar `analysis/summaries/key_statements.json`, row key -> sentence <= 160 characters); rebuild, render, hygiene clean. Its content REQUESTS (operator per interface, ranking and dependencies of migration tasks, security flag, so-what per requirement …) go to the owning consolidator (D3/D4) or unit analyst with a mini gauntlet on the changed claims; its ESCALATIONS go to the lead as registered questions, and a lead decision on a major cluster is recorded with `dbcx gate decide <n> <cluster> "…"` (then `dbcx gate_aggregate <n>` again). No won't-fix list: every blocker and major cluster is fixed or escalated before round n+1; a cluster "unchanged since round k" needs a different mechanism.
4. Round n+1 from step 1 with ALL personas and the verifier on a fresh read; their briefs carry each persona's previous issues and `dbcx gate diff <n+1>` (tool diff of the customer workbooks) - no orchestrator addendum explaining what "cannot be changed".

## Phase 6 – Report
`docs/FINAL_REPORT.md` (English; real numbers: rounds and final averages per scope, failed scopes, gate scores per persona × deliverable × dimension, open issues, assumptions) and `docs/MODULE5_CANDIDATES.md` (8-12 feature candidates for the optional deep-dive with D2/D3/D4 ids, ranked by the blocker- and major-impact migration tasks that affect their requirements). Handover to a following estimation run (after the client saw the deliverables, on the user's word): `dbcx handover export` releases code-inventory, customization-depth, requirements-coverage, target-readiness and requirements-set; the NR rows' client decisions come back as a new requirement workbook version. `dbcx learn export` (on the user's word) so verified facts and learnings reach the plugin maintainer. Tell the user where everything is; never claim a pass that did not happen.

## Guard rails
- One unit per agent; code reading outside the assignment is forbidden (critic 1 checks evidence paths). Vendor/standard code is readable by everyone.
- Nothing aggregated is typed into Excel or diagrams; only `dbcx build_*` write deliverables; only the orchestrator runs them.
- Real numbers, failed rounds and open issues are reported. Scores are never edited by hand (`build_excel` verifies the checksums written by `score_aggregate`).
- Delegation budget: spawn only what this plan names; critics persist per scope (rounds are messages); agents spawn helpers on the HELPER MODEL only; never redo a sub-agent's work; briefs come from `dbcx render brief --out`, the D1 digest from `dbcx render handover`, the consolidation input from `dbcx render digest`.
- State is verified, not trusted: `dbcx status verify` on every resume; an agent whose output is on disk is delivered; a critic file is converted once; a passed round is never re-opened; every fix hint and every orchestrator figure is a hypothesis until the role that owns the evidence reproduced it.
- Client-facing text speaks about the shop: no rounds, corrections, reviewers, sessions or edit dates in any cell (lint); correction history lives in the claims' `history` column and in `analysis/gauntlet/`.
- Read-only repository. Do not run: {list:rules.do_not_run}. Do not modify repository files.
- No client code or client name to external services. Web lookups only for vendor documentation with generic queries.
