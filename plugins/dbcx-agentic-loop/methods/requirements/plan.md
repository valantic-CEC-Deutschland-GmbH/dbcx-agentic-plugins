# Orchestration plan – requirements for the {system.type} of {engagement.client}

Trigger: the user says **"Execute the plan"** after (a) `dbcx check_fill` reports 0 placeholders, (b) `dbcx smoke requirements` ends with SMOKE TEST OK, (c) the client's material lies in `input/` (by date, never modified). Run everything below without asking questions; decisions go to `state/STATUS.json` → `assumptions[]` (`dbcx status assume ...`). Resume point after any interruption or context compaction: `dbcx status verify`, then `dbcx status next`. "How far are we?" at any time → `dbcx progress` plus the progress-reporter brief. Feedback given in chat during the run → `dbcx status feedback add "..."` immediately.

Plugin: `{plugin}` (tools `dbcx <tool>` or `python3 {tools}/<tool>.py`; roles are the plugin agents `dbcx-agentic-loop:<role>`). Every agent is spawned from a brief FILE: `dbcx render brief ... --out [--addendum <file>]` writes `analysis/briefs/<agent>[-rN].md` and prints path, MODEL and agent name; the prompt references the path (the spawn hook checks path and model and registers the agent in `in_flight`). Rounds ≥ 2 need `--addendum <file>` (or `--no-addendum`). Critics stay alive per scope: later rounds are SendMessage calls with the new delta, not new spawns.

The unit of analysis is the **{unit.noun}**; one analyst per {unit.noun}. Deliverables in `{languages.deliverable}`; chat and agent reports English.

| | Deliverable | Built by (orchestrator only) | From |
|---|---|---|---|
| D1 | `deliverables/{deliverables.D1.file}` | `dbcx build_excel D1` | `corpus/index.json` + `analysis/inventory/source_inventory.md` |
| D2 | `deliverables/{deliverables.D2.file}` | `dbcx build_excel D2` | `analysis/scopes/*.md` + `analysis/consolidated/SET.md` |
| optional | `deliverables/{deliverables.estimation_sheet_export.file}` | `dbcx export_estimation_sheet` | `analysis/consolidated/SET.json`, only when `deliverables.estimation_sheet_export.enabled` |
| artefact | `@project/handover/requirements-set-*.json` + `state/requirements.json` | `dbcx export_requirements`, `dbcx handover export requirements-set` | `analysis/consolidated/SET.json` |

The biggest risk of this method is an **invented requirement**. Everything below exists to make one impossible to hide: a locator on every row, a corpus a critic can grep, a client critic whose only job is to open those locators, and a Traceability sheet the client can check line by line.

---
## Lean variant (run.json `profile: lean`)
One analysis over everything, for material the consolidator can read whole (`dbcx status next` walks it). Phase 0 as below, plus: add the documentation hosts the standard facts will cite to the run.json `evidence_bases` entry `standard-docs` (`domains`) - quotes are required. Then the rulings (`dbcx rulings draft|add|answer|done`, required) → Phase 1 with every claim carrying a verbatim quote and **no critic** (CHECK, `dbcx extract_claims D1 --round 1` runs the quote check, `dbcx evidence check D1`, `dbcx score_aggregate D1 1`: pass rule `defects+quotes`) → `dbcx render handover`, **no** discover / plan_waves / Phase 2 → Phase 3 with the SET consolidator writing every requirement row from the corpus, epic by epic (`dbcx render digest SET` lists the epics with their sources) and the **standard critic only** (one round, one rework round for defects) → release the question batch (`dbcx questions release --all`) → Phases 4 to 6 unchanged.

## Phase 0 – Preflight (orchestrator)
1. `dbcx check_fill` → 0. `dbcx smoke requirements` → SMOKE TEST OK. `dbcx md_to_json --generate` (templates and schemas current).
2. **Index the corpus**: `dbcx corpus index` (walks `{project}/input`), then `dbcx corpus list`. Read the counts: sources, unextractable, partial. Where a PDF has no text layer or a deck is image-only, ask the client for the source file – as a client question, not as an inference (`dbcx questions add intake client "..." --effect "..."`). Miro boards belong in the corpus as exports (`*.miro.json`), never called live during the run. Re-index only from here, never from inside an agent.
3. `dbcx intake` (defects of the imported inputs become CLIENT questions, not review findings) → `docs/INTAKE.md`. `dbcx handover import client-context` / `dbcx handover import system-inventory` when an earlier run released them (they materialise under `state/`, are cited as `HO-<type>#<id>` and are never re-reviewed).
4. `dbcx status init`. Researcher only when a catalogue slot is set: spawn `dbcx-agentic-loop:researcher` from `dbcx render brief research --out`; it resolves the catalogue seed's *(verify)* items into `reference/platform-standard.md` section 7. Without a catalogue slot, record the assumption that the completeness check rests on best practice only.
5. `dbcx status set phases.preflight.status '"done"'`; log; record assumptions.

## Phase 1 – Source inventory and epic structure → D1
1. Spawn `dbcx-agentic-loop:inventory-analyst` from `dbcx render brief inventory --out` (its brief carries the corpus statistics it must reconcile its Sources table with). Convert once: `dbcx md_to_json inventory analysis/inventory/source_inventory.md`; on WARNING/INVALID send the output back. Every SRC id of the index needs a row; every epic needs at least one source; `activation` and `estimated_requirements` must be filled for every epic.
2. Gauntlet D1: `dbcx extract_claims D1 --round <n>`; `dbcx evidence check D1` (dangling locators); spawn `critic-client` and `critic-standard` from `dbcx render brief critic client D1 <n> --out` / `... standard D1 <n> --out` (round 1) or SendMessage the new delta to the running critics (round ≥ 2, brief with `--addendum`); convert each once; `dbcx score_aggregate D1 <n> --dry-run`, then for real. Read the issues file (blocking verdicts, divergence, notes on passing claims). Fail → issues file to the analyst, next round (max `scoring.max_gauntlet_rounds`). Passed → `dbcx render handover`; wording notes → `dbcx render brief postpass D1 --out`.
3. `dbcx discover` (epics → `state/scopes.json`; kebab-case scope ids, size = `estimated_requirements`, out-of-scope epics skipped) and `dbcx plan_waves` → `state/WAVES.json`. Check the plan: the functional epics must come before the technical ones that depend on them (`wave_rule: dependency`), an epic with ≤ 5 expected requirements runs light. `dbcx status scope <name> '{"wave": n, "status": "open"}'` for every epic; set `phases.waves.total_waves`. Overrides only via `--light/--skip` plus an assumption.
4. `analysis/summaries/D1.md`, then `dbcx build_excel D1`. Spawn one gate persona (the least technical) on D1 for an early read; queue its presentational issues.

## Phase 2 – Waves (one requirement set per {unit.noun})
Before wave 1: the rulings step (`dbcx rulings draft` -> 10-25 cross-cutting questions with options and a recommendation -> the lead answers them in one sitting -> `dbcx rulings done`, or `dbcx rulings skip`; `dbcx status next` holds wave 1 for it under `human_input.rulings: required`); under `human_input.release: batched` release the question batch at every wave gate and phase end with `dbcx questions release` after reviewing its `related` neighbours and duplicates.
For wave N (max `scoring.max_agents_per_wave` agents in parallel; wave N+1 is rendered and spawned only after wave N is closed):
1. `dbcx render brief analyst <epic> --out` per epic (context incl. MODEL, CLAIM CAP, the epic's SRC ids with titles and extraction quality, the corpus grep commands, the D1 handover section, routed open questions, resume note).
2. Spawn `dbcx-agentic-loop:analyst` agents named `analyst-<epic>` in one message, each with its MODEL (light epics on `models.analyst_light`). Wait. Before re-spawning anything: `dbcx status inflight list` / `dbcx status verify` – output on disk = delivered.
3. On report: `dbcx md_to_json epic analysis/scopes/<epic>.md` (once; read WARNINGs); `dbcx status inflight done analyst-<epic>`; `dbcx evidence check <epic>` – a dangling locator goes straight back to the analyst, it is the one defect no critic can repair. Open questions → `dbcx questions import <epic>` (registers the analyst's rows with their proposed answers; `dbcx questions add` for questions of your own), later `answer|scored|forward`; everything with `to = client` stays open and becomes the Open_Questions sheet. Record learnings with `dbcx learn add`.
4. Gauntlet per epic as soon as the draft converts OK: `dbcx extract_claims <epic> --round <n>`; critics from `dbcx render brief critic <critic> <epic> <n> --out` (round 1) or SendMessage with the new delta (round ≥ 2; brief with `--addendum`); convert once each; `dbcx score_aggregate <epic> <n> --dry-run`, then for real. Light epics: light gauntlet. A `false` verdict on a requirement row means an invented requirement – it blocks the pass regardless of the average, and the fix is the row, not the wording. `status: final` only when passed (or `failed-gauntlet` after the last round).
5. Corrections that touch shared vocabulary (a domain term, a system name, a priority reading) are forwarded to the other epics that use it; a corrected figure gets `dbcx grep_scopes` before and after.
6. Wave N is closed when every one of its scopes is `final`, `failed-gauntlet` or `skipped`; only then is wave N+1 rendered and spawned - never while a wave-N scope is still analysing, in gauntlet or in rework. Dependencies being final is necessary, not sufficient. Overlapping waves multiply the live agents (one analyst plus the client critic and every standard critic per scope in gauntlet) and have run a session out of budget mid-round, killing agents before they could finish. `dbcx render brief analyst` refuses a scope whose wave is not the open one; `--force` plus a logged `dbcx status assume <reason>` is the only way past it. Persist `phases.waves.current_wave`. After the first `dbcx build_excel D2 --interim`, one gate persona reads it early.

## Phase 3 – Consolidation (SET)
1. All epic analyses final/failed-gauntlet. `dbcx render digest SET` (every requirement row with its citing claim ids, the per-epic counts against D1's estimate, the contradictions, the open questions and the FR↔TR candidates).
2. Spawn `dbcx-agentic-loop:consolidator` from `dbcx render brief consolidate SET --out`. Convert once: `dbcx md_to_json requirements_set analysis/consolidated/SET.md`. Follow-ups to a running consolidator go as ONE message; never extract while it runs (`extract_claims` refuses).
3. Gauntlet SET (client and standard critics, kept alive across rounds, deep_reasoning standard critic). Put the rows the consolidator reports as changed (merges, renumbering, calibration) into the critic brief by hand – changed table rows are invisible to the claims register. The coverage report shows rows no claim cites.

## Phase 4 – Build deliverables and release the artefact (orchestrator)
1. Write `analysis/summaries/D2.md` (deliverable language, no typed-in numbers, only passed claims, no process language).
2. `dbcx build_excel --all` (+ `--internal` for the team's review-notes workbooks). The build runs `dbcx lint_deliverable` and rejects process language – fix the analyses (postpass briefs), never the workbook. Check with openpyxl: every sheet present, Overview charts present, `Open_Questions` present, Claims scored for every claim, no formula referencing a missing sheet, and the Traceability sheet holding one row per requirement AND locator.
3. `dbcx export_requirements` → `state/requirements.json` in the engine's requirements shape (`id`, `group` functional|technical, `epic`, `title`, `description`, `acceptance_criteria`, `exclusions`, `references`, `phase`, `sources`, `priority`; the untouched `type` travels along). This is what makes the set importable: a later `tech-scoring` or `tech-fit-estimation` run reads exactly this file. Refuses while SET is `status: draft`.
4. Optional, only when `deliverables.estimation_sheet_export.enabled` is true: `dbcx export_estimation_sheet` → `deliverables/{deliverables.estimation_sheet_export.file}` in the client's EstimationSheet shape (sheets `Functional Requirements` / `Technical Requirements`, columns #, ID, Epic, Title, Description, Open Question; formula-free, so their columns F.. survive). The deliverable of record stays `{deliverables.D2.file}`.
5. `dbcx status set phases.excel_build.status '"done"'`.

## Phase 5 – Final gate
1. Spawn `dbcx-agentic-loop:gate-persona` once per persona in `scoring.gate_personas` in parallel (`dbcx render brief gate <persona> <round> --out`, MODEL from the gate profile). Convert each (`dbcx md_to_json gate ...`), `dbcx gate_aggregate <round>`.
2. Fail → blockers first: understandability/actionability → `overrides/deliverables.{languages.deliverable}.json` texts, README, Management_Summary, column order; provability → the owning analyst or the consolidator adds locators (mini gauntlet round on changed claims). Rebuild, rerun the failed personas plus one that passed. Max `scoring.max_gate_rounds` rounds.

## Phase 6 – Release and report
1. `dbcx handover export requirements-set` after the client has seen the deliverables (hash-stamped snapshot in `{project}/handover/` with the passed claim ids). `dbcx handover list` to confirm. A chained run imports it with `dbcx handover import requirements-set`.
2. `docs/FINAL_REPORT.md` (English; real numbers: requirements by type and priority, traceability share, inferred rows, missing technical requirements, catalogue gaps, rounds and final averages per epic, failed epics, gate scores per persona × deliverable × dimension, open client questions, assumptions). `dbcx learn export` (on the user's word) so learnings and verified facts reach the plugin maintainer. Tell the user where everything is; never claim a pass that did not happen.

## Guard rails
- One epic per agent. An analyst reads only its own epic's sources; what it needs from a neighbour is an `Open questions` row, never a peek.
- Every requirement row carries ≥ 1 corpus locator or the literal `inferred` with a claim behind it. A row with neither is an invented requirement and blocks the pass.
- Priority, release and exclusions come from the sources. `unknown` is a result, not a gap to fill.
- The client's material is read-only and never leaves the run: no client name, epic name or corpus locator in a web query (hook-enforced). The standard critic has no corpus access, the client critic no catalogue and no web.
- Nothing aggregated is typed into Excel; only `dbcx build_excel` / `dbcx export_*` write deliverables, and only the orchestrator runs them.
- Real numbers, failed rounds and open questions are reported. Scores are never edited by hand (`build_excel` verifies the checksums written by `score_aggregate`).
- Client-facing text speaks about the client's requirements: no rounds, corrections, reviewers, sessions or edit dates in any cell (`dbcx lint_deliverable`); history lives in the claims' `history` column.
- Do not run: {list:rules.do_not_run}. Do not modify anything under `input/` or `corpus/`.
