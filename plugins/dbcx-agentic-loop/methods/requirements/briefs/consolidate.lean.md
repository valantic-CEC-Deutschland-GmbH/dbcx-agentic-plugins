## ROLE INSTRUCTIONS (requirements: set consolidator, SET -> D2, profile lean)
There are no epic analysts in this run: you write the ONE numbered requirement set for the {system.type} directly from the client's material, epic by epic: `analysis/consolidated/SET.md` (template `templates/requirements-set.md`). Head field `system_type` = the SYSTEM TYPE of the CONTEXT. Start from the DIGEST (the inventory's epics with their sources, expected requirement counts and claim ids, the corpus index); then read every source an epic names completely before you write one of its requirements.

1. **Extract.** One requirement per row, one capability per row, in the client's vocabulary (METHOD NOTES). `epic` = the epic id of the inventory. A row the material states carries at least one corpus locator in `source_locators` (`SRC-nnn#anchor`, the anchor above the passage); a row you infer carries only the literal `inferred`, names the inference in its description and gets its own claim. Priority and release only as a source states them - otherwise `unknown`, which is not a defect.
2. **Dedupe while you write.** The same capability in two epics' material is ONE row: keep the clearer wording, keep the UNION of the locators. Two rows that merely sound similar but differ in scope stay two rows and say how they differ.
3. **Number globally.** FR-001.. in epic order, then TR-001.., then NFR-001..; no gaps, no reserved ranges; `duplicates_of` stays empty (no per-epic ids exist in this run). `status` = `confirmed` (a locator carries it), `inferred` (only `inferred` in the locator column, with its claim), `question` (the row depends on an open client question - name the question id in the acceptance hint).
4. **Contradictions.** Where two sources disagree (priority, scope, exclusions, who wants it), cite BOTH, write the row as the newer or more authoritative source states it only when a document says which one wins, and otherwise make it a client question - every contradiction also becomes a claim.
5. **FR<->TR cross-check** (the sheet a reader trusts this set for): one Crosscheck row per functional requirement that moves data across a system boundary - `has-tr` with the technical requirement id, or `missing-tr` with the interface named in the note - and one row per technical requirement nothing needs (`orphan-tr`, `functional_requirement` = `none`, note says whether it is an undocumented driver or an invented requirement). Every `missing-tr` becomes either a new technical requirement (with `inferred` in the locator column, an own claim, and `status: inferred`) or a client question - say which, never both.
6. **Catalogue gaps.** One row per capability of the reference catalogue (CATALOGUE) that no requirement covers: `covered_by` empty, `decision` = `in-scope` (you add a requirement - then name its new id in `covered_by`), `out-of-scope` (the client's material excludes it - name the locator) or `question` (nobody said anything). Never copy a catalogue entry into the requirement list as if the client had asked for it. Without a configured catalogue the table holds exactly one row (`catalogue_id: none`, `decision: question`) stating that no reference catalogue was configured and the completeness check therefore rests on best practice only.
7. **Client questions.** Every question only the client can answer (contradictions, missing priorities that decide a release, catalogue decisions, missing interfaces), de-duplicated, each with WHICH requirement ids or which priority its answer moves. This table is a deliverable of its own - the engine puts it on every workbook.
8. **Claims** `C-SET-NNN`: every requirement whose wording is not a near-copy of its passage, every contradiction, every `missing-tr`, every `orphan-tr`, every catalogue decision other than `in-scope`, every requirement you inferred, plus 5-10 cross-cutting assessments naming requirement ids (where the material is strong, where a whole epic rests on one passage, which priorities are actually unstated, what the set does NOT cover). Fact claims cite the corpus locator with a verbatim `quote`; report a divergence between the inventory's expected requirement count and what you wrote per epic.

Report (English, <= 15 lines): rows per epic against the inventory's estimate, requirements by type and priority, traceability share, inferred rows, contradictions, cross-check result (has-tr / missing-tr / orphan-tr), catalogue decisions, quotes not verified, open client questions, learnings.
