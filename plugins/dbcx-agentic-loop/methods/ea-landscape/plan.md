# Orchestration plan – {engagement.client}, enterprise / CX architecture: as-is landscape and target architecture (D1–D4)

Trigger: the user says **"Execute the plan"** after (a) `dbcx check_fill` reports 0 placeholders, (b) `dbcx smoke ea-landscape` ends with SMOKE TEST OK, (c) the client's documents lie in `input/` (by date) and `dbcx corpus index` has run. Run everything below without asking questions; decisions go to `state/STATUS.json` → `assumptions[]` (`dbcx status assume ...`). Resume point after any interruption or context compaction: `dbcx status verify`, then `dbcx status next` (status-driven; the SessionStart hook prints verify automatically). "How far are we?" at any time → the `progress` sub-command of the skill. Feedback given in chat during the run → `dbcx status feedback add "..."` immediately.

Plugin: `{plugin}` (tools `dbcx <tool>` or `python3 {tools}/<tool>.py`; roles are the plugin agents `dbcx-agentic-loop:<role>`). Every agent is spawned from a brief FILE: `dbcx render brief ... --out [--addendum <file>]` writes `analysis/briefs/<agent>[-rN].md` and prints path, MODEL and agent name; the prompt references the path (the spawn hook checks path and model and registers the agent in `in_flight`). Rounds ≥ 2 need `--addendum <file>` (or `--no-addendum`). Critics stay alive per scope: later rounds are SendMessage calls with the new delta, not new spawns. Orchestrator session: use the semantic orchestrator profile. Deliverables speak about the client's landscape only – no rounds, corrections or reviewers in any cell (`dbcx lint_deliverable` guards it).

Scope of this study: **{landscape.focus}**. Strategic frame: **{strategy.vision}** Horizon: **{strategy.horizon}**. Unit of analysis: one system ({system.noun_plural}, categories {list:system.categories}). Deliverables in `{languages.deliverable}`; chat and agent reports English.

The client question list is a deliverable in its own right: every mastership conflict, every `visual, unverified` locator and every assumed interface becomes a `to = client` question with the effect of its answer, and the engine puts them on the `Open_Questions` sheet of every workbook.

## Lean variant (run.json `profile: lean`)
One analysis over everything, for a corpus the consolidator can read whole (`dbcx status next` walks it). Phase 0 as below, plus: add the documentation hosts the standard facts will cite to the run.json `evidence_bases` entry `standard-docs` (`domains`) - quotes are required. Then the rulings (`dbcx rulings draft|add|answer|done`, required) → Phase 1 with every claim carrying a verbatim quote and **no critic** (CHECK, `dbcx extract_claims D1 --round 1` runs the quote check, `dbcx evidence check D1`, `dbcx score_aggregate D1 1`: pass rule `defects+quotes`) → `dbcx render handover`, **no** discover / plan_waves / Phase 2 → Phases 3 and 4 with the consolidator reading the corpus (`dbcx render digest <X>` carries the inventory and the corpus index; the interfaces come from the documents, the mastership conflicts from the inventory; the conflict register is a checklist in the consolidator brief - no routing, no hold) and the **standard critic only** (one round, one rework round for defects) → release the question batch (`dbcx questions release --all`) → Phase 5 with all four workbooks: D2 is built from the inventory's system rows and data objects and the FLOWS flows (one interface row per flow end); capabilities, pain points and constraints need system analysts and read `not assessed` → Phases 6 and 7 unchanged.

## Phase 0 – Preflight (orchestrator)
1. `dbcx check_fill` → 0. `dbcx smoke ea-landscape` → SMOKE TEST OK. `dbcx md_to_json --generate` (templates and schemas current).
2. `dbcx corpus index` over `input/` → `corpus/index.json`, `corpus/text/SRC-nnn.md`, `corpus/unextractable.md`. `dbcx corpus list` – check the source count against what the client handed over, and note every source whose quality is `partial`, `none` or `unextractable`. Missing extractors (`pdftotext`, `python-docx`, `python-pptx`) are installed before the run, never worked around by reading a PDF by hand.
3. `dbcx intake` → `docs/INTAKE.md` plus one client question per defect class (unextractable sources, sources without a text layer). `dbcx status init`.
4. Knowledge: a `reference-architecture` pack is optional (`dbcx knowledge sources` shows what is set). When one is set, spawn `dbcx-agentic-loop:researcher` from `dbcx render brief research --out`; it resolves every *(verify)* item of the pack seed into `reference/platform-standard.md` section 7 (`dbcx reference add`, ids `PS-7-NNN`). Without a pack, record the decision as an assumption – the standard reviewer then names its own reference with a date.
5. `dbcx status set phases.preflight.status '"done"'`; log; record assumptions.

## Phase 1 – Inventory → D1
1. Spawn `dbcx-agentic-loop:inventory-analyst` from `dbcx render brief inventory --out`. Convert once: `dbcx md_to_json inventory analysis/inventory/landscape_inventory.md`; on WARNING/INVALID send the output back. The `relevance` column (core | peripheral | out-of-scope) must be filled for EVERY system – `dbcx discover` reads it.
2. Gauntlet D1: `dbcx extract_claims D1 --round <n>`; `dbcx evidence check D1` (dangling locators); spawn `critic-client` and `critic-standard` from `dbcx render brief critic client D1 <n> --out` / `... standard D1 <n> --out` (round 1) or SendMessage the new delta to the running critics (round ≥ 2, brief with `--addendum`); convert each once; `dbcx score_aggregate D1 <n> --dry-run`, then for real. Read the issues file (blocking verdicts, divergence, notes on passing claims). Fail → issues file to the analyst (SendMessage), next round (max `scoring.max_gauntlet_rounds`). Passed → `dbcx render handover`; post-pass wording notes → `dbcx render brief postpass D1 --out`.
3. `dbcx discover` → `state/scopes.json` (group = category, depends_on = the systems a system receives data from, size = interfaces mentioned, light = peripheral, skip = out-of-scope). `dbcx plan_waves` → `state/WAVES.json` (dependency rule: a system is scheduled once the systems it receives data from are in an earlier or the same wave). Review the plan, then `dbcx status scope <name> '{{"wave": n, "status": "open"}}'` for every system and set `phases.waves.total_waves`. Overrides only via `--light/--skip` plus an assumption.
4. Client questions from the inventory: `dbcx questions add inventory client "..." --effect "..."` for every mastership conflict and every unextractable source the deliverable depends on.
5. Write `analysis/summaries/D1.md` after the gauntlet passed; `dbcx build_excel D1`; `dbcx build_landscape_diagram --as-is` (the flow arrows appear once FLOWS exists – regenerate then). Spawn one gate persona (the least technical) on D1 for an early read; queue its presentational issues.

## Phase 2 – Waves (one analyst per system → D2)
Before wave 1: the rulings step (`dbcx rulings draft` -> 10-25 cross-cutting questions with options and a recommendation -> the lead answers them in one sitting -> `dbcx rulings done`, or `dbcx rulings skip`; `dbcx status next` holds wave 1 for it under `human_input.rulings: required`); under `human_input.release: batched` release the question batch at every wave gate and phase end with `dbcx questions release` after reviewing its `related` neighbours and duplicates.
For wave N (max `scoring.max_agents_per_wave` agents in parallel; wave N+1 is rendered and spawned only after wave N is closed):
1. `dbcx render brief analyst <system> --out` per system (context incl. MODEL, CLAIM CAP, the inventory row, the data objects that name the system, the SRC ids that mention it, the grep hint, the handover section, routed open questions, resume note).
2. Spawn `dbcx-agentic-loop:analyst` agents named `analyst-<system>` in one message, each with its MODEL (peripheral systems on `models.analyst_light`). Wait. Before re-spawning anything: `dbcx status inflight list` / `dbcx status verify` – output on disk = delivered.
3. On report: `dbcx md_to_json system analysis/scopes/<system>.md` (once; read WARNINGs); `dbcx status inflight done analyst-<system>`; open questions → `dbcx questions import <scope>` (registers the analyst's Open questions rows with their proposed answers; `dbcx questions add` for questions of your own), later `answer|scored|forward`. A question with `to = inventory` is answered by the orchestrator from the D1 analysis or, if the inventory is wrong, by a post-pass correction of D1 – never by the analyst adding a system to its own tables. Record learnings with `dbcx learn add`.
4. Gauntlet per system as soon as the draft converts OK: `dbcx extract_claims <system> --round <n>`; `dbcx evidence check <system>`; critics from `dbcx render brief critic <critic> <system> <n> --out` (round 1) or SendMessage with the new delta (round ≥ 2, brief with `--addendum`); convert once each; `dbcx score_aggregate <system> <n> --dry-run`, then for real. Light-pass systems: light gauntlet (`max_gauntlet_rounds_light`, `models.critic_client_light`). On fail SendMessage the issues file to `analyst-<system>`. `status: final` only when passed (or `failed-gauntlet` after the last round); wording notes → `postpass` brief.
5. A corrected public fact (a system's version, an owner, a mastership claim) is forwarded to the systems that cite it; a corrected figure gets `dbcx grep_scopes` before and after.
6. Wave N is closed when every one of its scopes is `final`, `failed-gauntlet` or `skipped`; only then is wave N+1 rendered and spawned - never while a wave-N scope is still analysing, in gauntlet or in rework. Dependencies being final is necessary, not sufficient. Overlapping waves multiply the live agents (one analyst plus the client critic and every standard critic per scope in gauntlet) and have run a session out of budget mid-round, killing agents before they could finish. `dbcx render brief analyst` refuses a scope whose wave is not the open one; `--force` plus a logged `dbcx status assume <reason>` is the only way past it. Persist `phases.waves.current_wave`. After D2 is first built (`dbcx build_excel D2` or `--interim`), one gate persona reads it early.

## Phase 3 – Consolidation FLOWS → D3
1. All system analyses final or failed-gauntlet. `dbcx build_excel D2` as orientation. `dbcx render digest FLOWS` (every interface, ownership and open-question row of every final system analysis with the claim ids that cite it, plus the pairs described from both ends).
2. Conflicts first (`dbcx status next` runs `dbcx conflicts detect` and holds the phase while one is open): the register `analysis/consolidated/CONFLICTS.json` lists every interface whose two ends disagree (direction, style, frequency, data objects) and every data object with more than one claimed master (inventory + Data ownership rows). `dbcx conflicts route` → per owning system `dbcx render brief analyst <system> --conflicts --out` → SendMessage to `analyst-<system>` (re-spawn with that brief if gone). The analyst settles a conflict with one claim of its analysis whose `quote` a document carries, or reports it undecidable: convert once, then `dbcx conflicts resolve CF-n --claim C-<system>-nnn --by <system>` (→ knowledge-base entry) or `dbcx conflicts undecidable CF-n --reason "..." --by <system>` (→ client question; word it in `{languages.deliverable}` with `dbcx questions edit`). A mastership conflict is resolved only by a document that settles it; two documents that merely both claim it stay undecidable. `dbcx conflicts skip --reason` only when no analyst can answer.
3. Spawn `dbcx-agentic-loop:consolidator` from `dbcx render brief consolidate FLOWS --out` (its CONFLICTS block lists the register: the resolved value with its claim, the question of an undecidable one). Convert once (`dbcx md_to_json data_flows analysis/consolidated/FLOWS.md`). Open questions → the owning `analyst-<system>` (re-spawn with its brief if gone); mastership conflicts → `dbcx questions add FLOWS client "..." --effect "..."`.
4. Gauntlet FLOWS (client and standard critics, kept alive across rounds, deep_reasoning standard critic). Put the table rows the consolidator reports as changed into the critic brief by hand – the coverage report shows the rows no claim cites.
5. `analysis/summaries/D3.md`; `dbcx build_excel D3`; `dbcx build_landscape_diagram --as-is` again (now with the flow arrows).

## Phase 4 – Consolidation TARGET → D4
1. FLOWS passed – this is a hard precondition: without `analysis/consolidated/FLOWS.json` the target consolidator must refuse. `dbcx render digest TARGET` (pain points, constraints, capabilities and ownership rows of all systems with their claim ids).
2. Spawn `dbcx-agentic-loop:consolidator` from `dbcx render brief consolidate TARGET --out` (its CONTEXT names FLOWS.md/FLOWS.json, the strategic statements with their locators, and the horizon). Convert once (`dbcx md_to_json target_architecture analysis/consolidated/TARGET.md`).
3. Gauntlet TARGET. The standard critic checks whether the proposed products can do what each option needs in the edition and version named; the client critic checks whether an option breaks a documented constraint. An option resting on a `visual, unverified` interface stays `confidence: low` with the question that would raise it.
4. `analysis/summaries/D4.md`; `dbcx build_excel D4`; `dbcx build_landscape_diagram --target`.

## Phase 5 – Build deliverables (orchestrator)
1. Write `analysis/summaries/D1.md` … `D4.md` (deliverable language, no typed-in numbers, only passed claims, no process language).
2. `dbcx build_excel --all` (+ `--internal` for the team's review-notes workbooks) and `dbcx build_landscape_diagram --png`. The build runs `dbcx lint_deliverable` and rejects process language – fix the analyses (postpass briefs), never the workbook. Check with openpyxl: every sheet present, Overview charts present, `Open_Questions` present, Claims scored for every claim, no formula referencing a missing sheet, no `unknown` mastership row without a client question. `dbcx status set phases.excel_build.status '"done"'`.

## Phase 6 – Final gate
1. Spawn `dbcx-agentic-loop:gate-persona` once per persona in `scoring.gate_personas` in parallel (`dbcx render brief gate <persona> <round>`). Convert each (`dbcx md_to_json gate ...`), `dbcx gate_aggregate <round>`.
2. Fail → blockers first: understandability/actionability → `overrides/deliverables.{languages.deliverable}.json` texts, README, Management_Summary, column order; provability → the owning analyst or consolidator adds locators (mini gauntlet round on the changed claims). Rebuild, rerun the failed personas plus one that passed. Max `scoring.max_gate_rounds` rounds.

## Phase 7 – Report and handover
`docs/FINAL_REPORT.md` (English; real numbers: rounds and final averages per scope, failed scopes, gate scores per persona × deliverable × dimension, open client questions with the effect of each answer, assumptions). `dbcx handover export system-inventory data-flows target-architecture` after the client has seen the deliverables – the passed system inventory is the input a requirements or technology-selection run starts from. `dbcx learn export` (on the user's word) so verified reference facts and learnings reach the plugin maintainer.

## Guard rails
- One system per agent; reading another system's analysis is allowed only for the finalized upstream systems the brief names. Nobody logs into a client system: this study reads documents.
- Every row carries a locator or the exact phrase `visual, unverified`; the latter always comes with a client question. `dbcx evidence check <scope>` before every gauntlet round.
- A mastership claim names the document that claims it. Two documents disagreeing is a finding and a client question, never a decision made by an agent.
- Never infer an interface from box adjacency in a diagram. Never invent a version, an owner, a hosting model or a date to fill a cell.
- Nothing aggregated is typed into Excel or a diagram; only `dbcx build_excel` and `dbcx build_landscape_diagram` write into `deliverables/`, and only the orchestrator runs them.
- The standard critic and the researcher never see the client's documents (hook-enforced); the client critic never uses vendor documentation. Web lookups are generic: no client name, no system name of the client, no corpus locator.
- State is verified, not trusted: `dbcx status verify` on every resume; an agent whose output is on disk is delivered; a critic file is converted once; a passed round is never re-opened.
- Client-facing text speaks about the landscape: no rounds, corrections, reviewers, sessions or edit dates in any cell (lint); correction history lives in the claims' `history` column.
- Do not run: {list:rules.do_not_run}. Client documents are read-only.
