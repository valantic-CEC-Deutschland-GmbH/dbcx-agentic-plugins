# salesforce-commerce pack notes

- **Why the source role was given, despite this being multi-tenant SaaS.** SaaS platforms are target-only *unless an inspectable code base exists*, and SFRA cartridges are the defensible exception. That applies here: a B2C Commerce project keeps its cartridges in ordinary version control under `cartridges/`, each with a `.project` and an SFRA `package.json`, with the base implementation in `app_storefront_base` and shared CommonJS code in `modules/`. Controllers, models, scripts, ISML templates, forms, hooks, Page Designer components, `steptypes.json`, `metadata/**` and `sites/site_template/**` are all readable, and the customisation depth of an SFCC shop can genuinely be assessed from that tree - which is what the source role is for. SiteGenesis projects are inspectable too, though with a different (pipeline-based) architecture that must be recognised rather than mistaken for SFRA.
- **The limit of that source role, stated in the pack itself.** Three things that decide behaviour are NOT in the repository and are called out in `as_source.snippets.active_units_config` and `version_markers`: the site's **cartridge path** (which cartridges are live and in which order - so which override actually wins), the **active code version**, and the **compatibility mode** (which API behaviour and deprecation set applies). Object metadata and site data in the repository are import artefacts that may not match the live instance. A code-only analysis must therefore request the cartridge path per site, the active code version, the compatibility mode, the effective site preferences and the current quota status before calling any cartridge dead or asserting an effective override. That caveat is what makes the source role honest rather than overreaching.
- **Seed content**: the B2C/B2B product split and its consequences, SFRA vs SiteGenesis vs headless, the dw.*/ISML development stack, Einstein, Page Designer, promotions and A/B testing, the B2B Commerce feature list on the Salesforce Platform, LINK cartridges, the Jobs Framework, MuleSoft, and the weakness table (B2B separate, proprietary stack, headless maturity, learning curve, SaaS constraints, data ownership, non-Salesforce CRM).
- **Structural knowledge** (general B2C Commerce knowledge, marked `*(verify)*`): the cartridge path resolution rule and its collision semantics (positional silent wins, properties files resolving as whole files, additive hook chains), `server.append/prepend/replace` with `module.superModule`, `hooks.json` extension points, custom attributes in `system-objecttype-extensions.xml` versus custom object types and their quotas, `services.xml` and `LocalServiceRegistry` profiles, `steptypes.json` custom job steps, the IMPEX WebDAV file interface, SLAS shopper authentication, the SCAPI Shopper and Admin/Data family list plus the legacy OCAPI path shapes, Custom APIs as the sanctioned gap-closer, and the SaaS boundary set - quota framework, no direct DB, no arbitrary background processes, code-version deployment.
- **api_name `SCAPI (Shopper + Admin APIs)`** with legacy OCAPI named explicitly in `docs_domains`, the seed and `knowledge.json`, because some admin resources still have no SCAPI successor and an integration design that assumes SCAPI-only coverage will find gaps late.
- **Content model**: `content_model_name` is "content asset / Page Designer component" / "Content-Asset / Page-Designer-Komponente". `content_model_notes` keeps the three mechanisms apart - content assets, Business-Manager-configured content slots, and Page Designer components - and states the headless consequence: `/shopper/experience` returns the page and component tree as JSON, so every component type needs a frontend counterpart, exactly as an SAP Composable Storefront target needs a component mapping.
- **No `adapter.py`** by design, so this pack cannot scan a source repository yet.

A researcher must resolve these first, in this order:
1. Which product the engagement is actually about - B2C Commerce or B2B Commerce on the Salesforce Platform. Getting this wrong invalidates every estimate.
2. Compatibility mode, SFRA base version (`app_storefront_base/package.json`), and whether the storefront is SFRA, SiteGenesis or headless.
3. The cartridge path per site and the active code version - requested from the client, since the repository cannot show them.
4. Which entitlements exist: Einstein, Page Designer, headless/SCAPI access, Omnichannel Inventory, Salesforce Order Management.
5. The LINK cartridge inventory with each cartridge's LINK version and maintenance status - the usual source of both functionality and upgrade debt.
6. The current quota status and the real collection sizes the design will touch, before any per-line-item or per-request integration is designed.
7. For a headless target: the full list of Page Designer component types in use, mapped against planned frontend components.
