# scayle pack notes

- **Roles = `["target"]` only, and `as_source` is omitted entirely.** SCAYLE is a fully managed SaaS commerce engine: the extension model is the API surface, webhooks and the add-on catalogue, and no code is deployed into the engine. The only code a project owns is its frontend, which is not the commerce platform and would not tell an analysis anything about platform customisation depth. SaaS platforms whose extension model is apps and scripts are target-only.
- **Seed content**: the ABOUT YOU origin and the roughly EUR 1.9B GMV claim, the component split (Commerce Engine, Storefront API, Admin API, Panel, Add-on API), the fashion-oriented variant model, the omni-channel add-on contents (store management, store locator, store inventory locator, click and collect, ship from store, PWA for staff), the wholesale module as the only B2B feature, customer groups and group-based price lists, Storefront Application and Storefront Hosting, webhooks, EU data residency, and the weakness table (B2B depth, market presence, partner ecosystem, documentation maturity, fashion focus, geographic reach, customisation effort).
- **Structural knowledge** (marked `*(verify)*` throughout the seed): the concrete Storefront API and Admin API resource families in `knowledge.json`, reconstructed from the vendor's component list plus general knowledge of API-first commerce engines - almost no resources are named by the vendor, so these are explicitly labelled best-effort in `_readme` and must be checked against the current API reference; the "no server-side extension point inside the engine" statement as the central architectural constraint; and the practical consequence that API rate limits, bulk-import throughput and webhook delivery guarantees must be obtained in writing before an integration is designed.
- **The modular-SaaS rule, stated in three places** (seed section 2, `critic2_focus`, `expected_blockers_d4`): on a platform sold as a core plus add-on modules with transaction-based elements, "standard" means "contracted". A documented feature that the client has not licensed is a gap, not coverage. This is the most likely way a SCAYLE fit estimation goes wrong.
- **Content model - the honest answer.** No CMS module is listed: the vendor material names product information management, media management, internationalisation and the Panel, and nothing about pages, layouts or components. `content_model_name` is therefore "content block" / "Content-Block", but `content_model_notes` says plainly that this term will usually refer to a block in an external headless CMS rather than a SCAYLE object, and that a project must estimate TWO content models - the entity-bound content SCAYLE owns (product, category, brand, promotion, store, SEO) and the editorial content that comes from the storefront application or an external CMS (landing pages, campaign pages, editorial components, legal pages, magazine content). `knowledge.json target_content_component_types` marks every entry with which side it belongs to. Whether a SCAYLE CMS or content module exists in the client's contract is the first thing a researcher must settle, because it materially changes the scope.
- **No `adapter.py`** by design, and none would be meaningful for a target-only SaaS pack.

A researcher must resolve these first, in this order:
1. What the client's contract actually includes - core plus which add-on modules (omni-channel, wholesale, others) - and the commercial mechanics (GMV or transaction elements, minimums, thresholds).
2. Whether a SCAYLE CMS or content module exists and is contracted; if not, which external headless CMS is assumed, since that is a second system in the landscape with its own content model and editorial workflow.
3. The current Storefront API and Admin API references: real resource names, protocol per family (REST and/or GraphQL), and whether GraphQL covers the same surface as REST.
4. The webhook event catalogue with delivery guarantees, retries and ordering, plus API rate limits and bulk-import throughput - in writing, before any integration design.
5. What Storefront Hosting actually manages (build, CDN, cache invalidation, preview environments, SLAs) versus what stays with the client.
6. Market coverage for every country in scope: tax, legal texts, payment methods, carriers, languages - the platform's strength is DACH and Europe.
7. Public references at the client's scale and vertical, given the limited market presence and partner ecosystem size.
