# spryker pack notes

- **Source-side conventions**: unit definition (noun Module, `manifest_file` only a fallback because project modules under `src/Pyz/<Layer>/<Module>` usually have no own `composer.json`, one unit = one module name merging its layers), `repo_roots` `["src/Pyz"]`, `standard_dirs` `vendor/spryker`, `vendor/spryker-shop`, `vendor/spryker-eco`, the category mapping (Yves -> frontend, Glue -> api, Zed GUI -> admin, `*Connector`/`*Api` -> integration, Client/Service -> facade, Zed Business -> core), `standard_unit_prefixes`, the entry-point patterns, the class-shadowing rule (a `Pyz\` subclass is the NORMAL pattern -> `extended` unless it replaces the vendor class in a dependency provider; a patched `vendor/` file is `core-patch`), deprecation patterns reframed as portability blockers, and `source_content_component_pattern`.
- **Target lists describe Spryker itself**: `target_api_endpoint_families` and `target_content_component_types` are Spryker Glue resources and Spryker CMS/content types. The Shopware target lists live in the `shopware` pack.
- **Structural knowledge (general platform knowledge, marked *(verify)* in the seed)**: concrete Glue resource names, Publish & Synchronize as the read-model mechanism and why it makes new customer-facing data a pipeline rather than a query, OMS state machines as the order process, the separate-applications constraint, the Docker SDK/PaaS hosting constraints, and the CMS pages/blocks/slots/content-items structure.
- **Roles = `["source","target"]`.** Source is well founded: `src/Pyz` over `vendor/spryker*` is an inspectable code base with firm conventions, and the conventions are specified closely enough for an adapter. Target is founded on the platform's positioning as one enterprises move TO.
- **No `adapter.py`.** An adapter would work as follows: `discover_units` groups `src/Pyz/*/<Module>` by module name, `parse_dependencies` reads `use Spryker\...` / `use Pyz\...` imports, `unit_signals` reads transfer.xml, Propel schema, DependencyProvider plugin stacks, facades/factories, Glue resource plugins, Yves controllers/widgets, `platform_facts` reads `composer.lock` and `deploy*.yml`.
- **What a researcher must resolve first**: (1) the module versions and the release group the project pins - there is no single platform version, and every feature claim needs a module name plus version; (2) for each required feature, whether the module ships a working storefront part or only Zed/Glue plus an integration guide; (3) Glue resource coverage resource by resource, and whether a resource lives in the Storefront or Backend API; (4) which suites are licensed (Marketplace, B2B capabilities); (5) which read models need a new Publish & Synchronize pipeline; (6) team size and seniority, which is the most common real blocker on this platform.
