# pimcore pack notes

- **The central editorial decision**: the framing "Pimcore e-commerce is a framework, not a finished shop" is treated as the load-bearing fact of this pack, not a footnote. It is stated in `research-seed.md` as a section 0 scope statement, in `as_target.snippets.content_model_notes`, and in `expected_hotspots_d3`, which opens by telling the reader to split every requirement into a data/content part (Pimcore's strength, usually standard) and a shop part (usually project work). Scoring Pimcore as a shop platform produces both false gaps on the PIM side and false coverage on the commerce side, and that is the classic error this pack exists to prevent.
- **Seed content**: the PIM/DAM/CMS/commerce combination, the E-Commerce Framework component list (Index Service, Pricing Manager, Cart Manager, Checkout Manager, Order Manager, Voucher System, payment framework), multi-tenant B2B/B2C, "most B2B features require custom development", the weakness table (not turnkey, commerce depth, learning curve, B2B, checkout, ecosystem, resources) and the fit criteria.
- **Structural knowledge** (general Pimcore and Symfony knowledge, marked `*(verify)*`): the `as_source` structural layer - `config/bundles.php` as the activation authority, the Extension Manager state trap in older lines, `var/classes/definition_*` as the schema source together with the trap that class definitions may exist only in the database, DI decoration and template shadowing under `templates/bundles/`, event subscribers and priorities, the E-Commerce Framework's configured extension points, Symfony Workflow as the workflow engine, Flysystem asset storage and the thumbnail pipeline, Messenger workers plus the maintenance cron, and the admin-UI line change (classic bundle vs the newer Studio UI).
- **Roles = `["target","source"]`**: source is included because a Pimcore installation is an ordinary Symfony application in version control - bundles with `composer.json`, project code under `src/`, standard code under `vendor/pimcore` - so the unit conventions can be named with confidence. The honest caveat, recorded in `as_source.snippets.schema_sources`, is that the data model itself may not be in the repository at all if class definitions were never exported.
- **api_name `Pimcore Data Hub (GraphQL) + REST`**: deliberately paired, because Data Hub GraphQL is the real integration surface while REST is thin - a read-only Simple REST adapter plus the newer Studio backend API, with the legacy Webservice REST API removed in the 10 line. Every entry in `knowledge.json target_api_endpoint_families` that names an operation uses a `<ClassName>` placeholder, because Data Hub schemas are generated per class and per configuration.
- **Content model**: `content_model_name` is "document editable / brick" / "Document-Editable / Brick" The pack keeps the three mechanisms apart - Documents plus editables (CMS), area bricks (the component type, always custom-built), Data Objects with localized fields and bricks (PIM content) - and states that nothing editorial renders out of the box.
- **No `adapter.py`** by design, so this pack cannot scan a source repository yet.

A researcher must resolve these first, in this order:
1. Is `pimcore/ecommerce-framework-bundle` in `composer.lock` at all, and which other `pimcore/*` bundles are installed - that single answer decides whether the installation is a shop or a PIM.
2. Pimcore major version and the bundle-split state (classic admin UI bundle vs Studio), plus the deprecations of that line.
3. Whether Data Object class definitions are exported to `var/classes/definition_*`; if not, request the export before making any data-model statement.
4. The project's Data Hub configurations - without them no GraphQL operation name and no integration contract can be written.
5. The product index type in the ecommerce-framework configuration (MySQL, optimized MySQL, Elasticsearch/OpenSearch) together with real object counts - this is the performance ceiling and the reindex cost.
6. Which payment provider bundles are maintained for the version in scope, and which checkout steps already exist.
7. Hosting model (self-hosted vs Pimcore Cloud), the Flysystem asset adapter, the Messenger worker supervision and the maintenance cron - none of them provable from the repository.
