# shopify-plus pack notes

- **Seed content**: overview and USP, ideal-customer-profile and fit questions, B2B on Shopify feature list, B2C features, key features (Functions, Checkout UI extensions, Flow, Launchpad, Hydrogen, Oxygen, Shop Pay), integration surface, strengths/weaknesses tables, ecosystem fit. All of it is marked *(verify)* in `research-seed.md`.
- **Structural knowledge (general platform knowledge, still marked *(verify)*)**: API versioning scheme (YYYY-MM) and the quarterly changelog, cost-based GraphQL rate limiting, the Online Store 2.0 content model (sections, blocks, JSON templates, section groups), metaobjects/metafields as the structured-content layer, the Customer Account API, Function target names and their no-network constraint, B2B catalogs/price lists as the pricing mechanism.
- **Roles = `["target"]` only, `as_source` omitted.** A Plus store is multi-tenant SaaS. What a client "has" is a theme repository, a set of installed apps, extension bundles and Functions - not a shop code base with units, manifests and a standard/custom split the scanner can inventory. A theme repo would produce a Liquid-file inventory, not an extension inventory, and app-owned logic and data are invisible from the repository. If a project ever needs a Shopify-as-source scan, that is a different adapter (theme + extension inventory) and should be argued for explicitly.
- **No `adapter.py`** (target-only pack).
- **`knowledge.json`** carries only the two target lists. `target_api_endpoint_families` mixes Storefront GraphQL operations, Admin GraphQL resources, the Customer Account API and Function targets because Shopify has no single path-based API surface - a reviewer must always name which API a claim belongs to.
- **What a researcher must resolve first**: (1) the pinned API version and its support window, plus anything the changelog removed since; (2) the current Plus plan matrix - which features are Plus-only and which are all-plan; (3) the final sunset state of checkout.liquid and Checkout Scripts and the published Checkout UI extension targets for the project's checkout requirements; (4) current variant/option limits and expansion-store count; (5) B2B on Shopify coverage for the project's approval, quote and punchout requirements; (6) current rate limits for the planned catalog/price/inventory sync volume.
- **Do not treat the fit questions as a verdict**: they are a questionnaire. The `expected_hotspots_d3` / `expected_blockers_d4` snippets are phrased as checks for exactly that reason.
