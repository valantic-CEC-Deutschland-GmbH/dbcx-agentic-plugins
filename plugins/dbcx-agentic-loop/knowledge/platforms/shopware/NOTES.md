# shopware pack notes

- **Seed content**: overview and USP, ideal-customer-profile and fit questions, B2B feature list (B2B Suite/Components), B2C features, key features (Shopping Experiences, Flow Builder, Rule Builder, sales channels, custom fields, app system, Elasticsearch), integration surface, strengths/weaknesses, plans (Community / Rise / Evolve / Beyond), ecosystem fit. Every line in `research-seed.md` is marked *(verify)*.
- **Structural knowledge (general platform knowledge, still marked *(verify)* in the seed)**: the three deployment models and their different constraints, the plugin-vs-app split and the SaaS app-only rule, DI decoration and the `Decorated` convention, `sw_extends` vs. full Twig override, EntityExtension vs. custom fields, the DAL, cms_page/section/block/slot as database data, concrete Store API and Admin API route families, the `plugin` DB table as the activation authority, the `shopware/commercial` package as the plan gate.
- **Roles = `["target","source"]`.** Target is obvious. Source is defensible because Shopware 6 self-hosted/PaaS installations are a real, inspectable code base with firm conventions: plugins under `custom/plugins` and `custom/static-plugins`, each with a `composer.json` of `"type": "shopware-platform-plugin"` and `extra.shopware-plugin-class`, standard code under `vendor/shopware`. Apps (`custom/apps/*/manifest.xml`) are covered in the snippets but are a thinner source surface - most of an app's logic sits on an external app server that is not in the repository.
- **The one thing an inventory must not overstate**: activation. Shopware keeps installed/active state in the `plugin` database table, not in the repository. A plugin folder proves the code exists, nothing more. `active_units_config` says this explicitly and demands a `plugin:list` output, a DB dump or merchant confirmation before anything is called live or dead. The same applies to Flow Builder flows, Rule Builder rules, admin-created custom field sets and import/export profiles - all database-only, all invisible to a code scan, all real migration scope.
- **No `adapter.py`** (by design). A source scan therefore needs one written first; the read order, override patterns and entry-point patterns in `pack.json`/`knowledge.json` are the specification for it.
- **What a researcher must resolve first**: (1) the exact 6.x minor from `composer.lock` (not `composer.json`) plus the deployment model, since SaaS changes almost every answer; (2) which required features are in `shopware/commercial` and under which plan; (3) Store API coverage route by route for the project's B2B and account flows; (4) the Flow Builder action catalogue and Rule Builder condition set of the target minor, and whether a custom rule provider is possible in the chosen deployment model; (5) `UPGRADE-6.x.md` for deprecations affecting the source plugins; (6) whether custom CMS element types exist in the source and who will re-implement their renderers if the target frontend is headless.
