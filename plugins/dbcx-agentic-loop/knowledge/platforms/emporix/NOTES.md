# emporix pack notes

- **Roles = `["target"]` only, and no `as_source` block.** Emporix is multi-tenant, API-first SaaS. There is no inspectable shop code base: extension is mixins, webhooks/events and the project's own services beside the platform. SaaS platforms of this kind are target-only.
- **No `adapter.py`** (nothing to scan).
- **This is a thinly sourced pack, and the files say so.** The vendor material names services but no paths and no versions. `target_api_endpoint_families` is therefore a RECONSTRUCTION of the vendor's `<service>/{tenant}/<resource>` shape on api.emporix.io, flagged as such in `knowledge.json` `_readme`, in `_stamp.verify_first` and in `api_families_hint`. Nothing from that list may be quoted in a deliverable before it is checked against the current API reference.
- **Content model follows the default** because no CMS is mentioned: `content_model_name` is "content item (external CMS)" / "Content-Element (externes CMS)", and `content_model_notes` states plainly that no page, template, slot or block resource exists, lists the content-shaped primitives that do (media/asset service, localized product and category texts, mixins, labels, site settings) and then the external-CMS components a project must supply.
- **The real constraints in `expected_blockers_d4` are ecosystem constraints, not API constraints:** young ecosystem, fewer partners and references, thinner documentation, and less proof at very large scale. They are named as checks (get two references at comparable scale, get a load reference or run a proof of concept), not as verdicts.
- **Not established here** and marked `*(verify)*`: every service name and path; the cloud provider and hosting regions; API rate limits and quotas; event/webhook delivery guarantees; the depth of the built-in PIM; the back-office UI scope for business users; whether a maintained storefront starter exists; the supported OCI/cXML punchout versions; and the environment/tenant count included in a subscription.
- A researcher should start on developer.emporix.io with the service catalogue and correct `knowledge.json` from there, then feed confirmed facts back through `dbcx learn export` to the maintainer.
