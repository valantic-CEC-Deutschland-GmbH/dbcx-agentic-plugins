# sylius pack notes

- **Seed content**: overview and USP, ideal-customer-profile and fit questions, B2B capabilities (Plus / B2B Suite), B2C capabilities, key features, plugin ecosystem, integration capabilities, strengths/weaknesses, editions (Standard MIT / Plus / B2B Suite extra), ecosystem fit, and the `/api/v2/shop|admin` shape. Every seed line is marked *(verify)*.
- **Structural knowledge (general Sylius/Symfony knowledge, marked *(verify)* in the seed)**: `config/bundles.php` as the activation authority, the resource-override mechanism (`sylius_<bundle>: resources: ... classes:`), Twig Hooks vs. full template overrides, the winzou / Symfony Workflow state-machine graph names, Doctrine migrations and translation entities, Payum, Symfony Messenger, the concrete `/api/v2/...` resource list, and the container-readiness caveats (media on the local filesystem, file-based cache/session).
- **The honest headline, stated in three places** (`content_model_name`, `content_model_notes`, `target_content_component_types`): Sylius core ships **no CMS** - no page, block or content entity, no page builder. Content is a decision between a community CMS plugin (BitBag CMS being the common one), a headless CMS, or custom entities, and each choice changes the frontend architecture. A content requirement must never be scored covered-standard on Sylius. `target_content_component_types` therefore mixes core content-bearing commerce data, plugin types and the custom option, each labelled.
- **Roles = `["target","source"]`.** Source is defensible: a Sylius shop is a plain Symfony application with firm conventions - project code under `src/`, Sylius under `vendor/sylius`, bundles registered in `config/bundles.php`, `composer.json` as the manifest. The caveat, stated in `active_units_config`: channel, payment, shipping and promotion configuration lives in the database, so the repository alone cannot prove a feature is live.
- **No `adapter.py`** (by design). The read order, override patterns and entry-point patterns in `pack.json`/`knowledge.json` are the specification for one. The unit granularity needs a decision at implementation time: many Sylius projects put everything in a flat `src/` without bundles, in which case the adapter must fall back to top-level namespaces or `src/<Domain>/` folders rather than to `composer.json` files.
- **What a researcher must resolve first**: (1) the Sylius minor from `composer.lock` and the Symfony major, plus `UPGRADE-*.md` between them; (2) what the current Sylius Plus / B2B Suite boundary contains, since the split moves; (3) for each required plugin: its Sylius-version compatibility and last-commit date - plugin maintenance is the platform's main third-party risk; (4) the content decision (plugin, headless CMS or custom) before any frontend estimate; (5) whether the 2.x storefront and its Twig Hooks are in play, because that changes every template-related estimate; (6) API Platform coverage operation by operation for the project's flows - a resource existing does not mean the operation exists.
