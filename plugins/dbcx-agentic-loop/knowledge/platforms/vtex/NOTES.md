# vtex pack notes

- **Seed content**: overview and USP, ideal-customer-profile and fit questions, B2B Suite feature list, B2C features, marketplace capabilities, key features (VTEX IO, Master Data, Intelligent Search, native OMS, franchise accounts, FastStore, Live Shopping), integration capabilities, strengths/weaknesses, ecosystem fit. Every seed line is marked *(verify)*.
- **Structural knowledge (general platform knowledge, marked *(verify)* in the seed)**: the per-service API structure with pub/pvt scopes and appKey/appToken authentication, concrete endpoint paths per service, orderForm as the cart and single source of truth, the order hook and order feed as the sanctioned order-event channel, Master Data v2 as the only sanctioned custom persistence, the IO workspace/app-version release model, Store Framework block names and the JSON block-tree page model, Site Editor as the merchant-facing content layer, and FastStore as a separate frontend that does not render Store Framework blocks.
- **Roles = `["target"]` only, `as_source` omitted.** VTEX is multi-tenant SaaS. A client's "code base" is a set of VTEX IO app repositories plus tenant configuration (trade policies, price tables, promotions, Master Data schemas, installed app versions) that lives in the platform, not in a repository. There is no manifest-and-standard-dirs split for the scanner to work with, and the majority of behaviour is configuration the repository cannot show. If a VTEX-as-source scan is ever needed, it is an IO-app inventory plus a tenant-configuration export - a different adapter, and it should be argued for explicitly.
- **No `adapter.py`** (target-only pack).
- **`knowledge.json`** carries only the two target lists. `target_api_endpoint_families` is grouped BY SERVICE rather than by one path prefix, because VTEX has no single versioned API - a reviewer must always name the service, the pub/pvt scope and, for B2B and reviews, the app that provides the capability.
- **Two facts that shape every assessment** and are stated in the snippets rather than buried: (1) the marketplace-first data model - sellers, offers, split orders and the fulfilment/marketplace role split shape catalog, pricing and OMS even for a single-seller business, so ERP interfaces must be designed around it; (2) the IO development model plus the regional talent and partner footprint is usually the first real project risk outside LATAM, ahead of any technical gap.
- **What a researcher must resolve first**: (1) regional availability and support coverage for the project's markets, including payments, logistics, tax and compliance; (2) which required capabilities are native, which are VTEX-maintained apps and which are partner apps, with the app versions installed on the account; (3) the current checkout extension points against the project's checkout requirements; (4) Master Data v2 query and scale limits before any custom entity is designed as an application database; (5) how organisation-specific B2B pricing maps onto trade policies and price tables, and the practical limit on trade policies; (6) whether the target frontend is Store Framework or FastStore, since content and component work does not transfer between them.
