# cx-reference pack notes

Provenance: hand-written on 2026-09-08 for the dbcx-agentic-loop plugin. Not converted from a product document — there is no vendor source for it. The content is generalised consulting practice from commerce and CX landscape assessments (ERP, PIM, DAM, CRM, CDP, CMS, OMS, search, iPaaS), with all client-specific material removed. Nothing in it is a verified external fact, which is why the pack carries no seeded reference-cache rows.

- **Written by hand, not derived**: capability map, SSOT table, integration-style table, anti-patterns and target-architecture option patterns. The register (terminology, table-driven structure, the habit of naming the failure mode rather than a vague weakness) follows `knowledge/platforms/sap-commerce/pack.json`, which was read as the style reference and not modified.
- **Kind and roles**: `kind: "reference-architecture"` (singular) in the folder `knowledge/reference-architectures/` (plural), `roles: ["reference_architecture"]`, snippets at the top level — non-platform packs are read from the top-level `snippets` map by the engine.
- **`docs_domains` is deliberately empty**: this pack is vendor-neutral and has no official documentation domain. Product-specific documentation belongs in the platform packs; putting a domain here would invite a critic to cite a vendor page as evidence for a vendor-neutral pattern.
- **No `adapter.py`, no `knowledge.json`**: the pack does not scan a repository and carries no target-version fact lists. The reference-architecture file set per the contract is pack.json, reference-architecture.md, research-seed.md, reference-cache.md, NOTES.md.
- **The reference-architecture.md is guidance, never a finding.** The opening paragraph says so, and the closing section repeats it. Anyone using the pack in a deliverable must cite the client's own systems and interfaces. If a reviewer sees a row from this file quoted as a client fact, that is a defect in the deliverable.
- **What a researcher must resolve first**, per engagement: the client's declared master per data domain and whether an attribute-level ownership list exists; the interface inventory with volumes, peaks and real consumers; the platform team's split between build and run capacity; and the licensing, hosting and residency constraints that bound the target. Without those four, the option patterns in section 5 cannot be assessed — their prerequisites are exactly those items.
- **How to extend**: keep the table shapes stable so the file remains usable as a gap grid — add rows, not columns. New anti-patterns follow the symptom / why / cost / way out shape, symptom first, because the symptom is what an analyst can observe. New target-architecture patterns must carry concrete prerequisites (a named owner, a signed-off decision, an existing inventory), a risk list and a sequencing suggestion; a pattern without prerequisites is marketing and should be rejected in review. Verified, dated, externally citable facts go into reference-cache.md, not into the guidance file.
